## 0. 结论速览

| 项 | 结论 |
|---|---|
| **推荐** | **先丙（最小止血，当天可做）+ 再甲（真正的解）**；**乙不足以解决用户诉求**（见 §4） |
| **一句话理由** | 用户要的是「课表里有课」。实测：全库 **139 节真实课时挂在一个没有任何学生的合班批上**，唯一在读学生的档案班**本周 0 节课** ⇒ 无论怎么改课表**读取口径**（乙），学生页面都会是空的；只有把课**排到学生真正所属的年级班**上（甲/丙），课表才会出现课程 |
| **乙单独能不能达成诉求** | **不能。** 乙只改「读什么」，改不了「有没有得读」（§4 逐条实测） |
| **丙单独能不能达成诉求** | **能**，但它与甲是**同一件事的两种做法**（手工 vs 按 §18 流程化 + 停用旧课时），差别在纪律与可回退性 |
| **甲能不能达成诉求** | **能**，但有一个必须单独守住的前提：**排课的目标班必须是学生的档案班**（§7 第 1 条） |
| **不可逆的一步** | **批量停用没有反向操作**：`edu_schedule` 只有 `deactivate_batch_sessions`（置 `state='cancel'`），全仓**没有** un-cancel 路由 ⇒ 见 §5.4 |

## 2. 断链的机制（写入者 / 读取者清单，符号级）

### 2.1 谁建 `op.session`

全仓（`custom_addons/` 逐文件）能建 `op.session` 的地方**只有两处**：

| 位置（符号） | 触发者 | 会被「报课 / 审批」触发吗 |
|---|---|---|
| `edu_schedule/controllers/main.py` 的 `EduScheduleTool._create`（周期排课确认） | 教务打开 `/timetable/bulk/create` | ❌ |
| `edu_schedule/controllers/main.py` 的 `EduScheduleTool._create_multi`（多班批量排课确认） | 教务打开 `/timetable/bulk/create` 且勾了多个班 | ❌ |

另有一处 `scripts/seed_demo.py`（演示数据），与业务无关。
（`edu_portal/controllers/grade_entry.py` 里那个 `Session.create` 是
**`op.exam.session`**，不是 `op.session` —— 名字像，别混。）

### 2.2 报课 → 审批 → 档案，三步各写什么

| 步 | 路由 / 符号 | 写哪张表 |
|---|---|---|
| 学生提交报课 | `POST /subject/enroll/save` → `edu_portal/controllers/enroll.py` 的 `EduEnrollPortal.enroll_save` | 只写 `op.subject.registration`（`state='submitted'`）；**不写档案、不写课节** |
| 教务审批通过 | `edu_portal/models/registration.py` 的 `OpSubjectRegistration.action_enroll_approve` | 只写 `op.student.course`（`subject_ids` 整体覆盖 / `state` / 必要时 `batch_id`）+ 单据自身 `state='approved'` |
| （基座后台另一条写手） | `openeducat_erp/openeducat_core/models/subject_registration.py` 的 `action_approve` | 同样只写 `op.student.course.subject_ids` |

触发 `action_enroll_approve` 的门户入口只有审批路由：
`enroll.py` 的 `set_state`（单条）与 `set_state_bulk`（批量）。
**两条都不碰 `op.session`。**

### 2.3 学生课表读什么

`edu_portal/controllers/scheduling.py` 的 `EduScheduling.student_timetable`：

- 角色判定 `current_student()` → `student_course()`
  （`edu_portal/controllers/main.py`：取**第一条** `state='running'` 的 `op.student.course`，没有则退回任意一条）；
- domain = `('batch_id','=',batch.id)` + 周窗口 + `('state','!=','cancel')`；
- **完全不读 `subject_ids`**（那是 LMS `/my/courses` 的口径，见 `edu_portal/controllers/lms.py`）。

### 2.4 断在哪一段

    报课 ──写──> op.subject.registration ──审批──> op.student.course.subject_ids
                                                        │
                                        ✗ 没有任何一步写 op.session
                                                        │
    学生课表 ──读──> op.session WHERE batch_id = 档案班   ✗ 读的是排课，不是选课

⇒ **两条完全不相交的链路**。这正是 `docs/plans/enroll-v2-design.md` 当年承诺
「课表即时联动」而实现没做到的地方（B1 诊断 §6.1 已记）。

## 3. 三条修法：动什么 / 谁承担风险 / 怎么回退 / 能不能达成诉求

### 甲（已拍板方向：`docs/plans/scheduling-overhaul-design.md` §18）

**动什么**（两步，都由教务在既有工具里做，**零新模型**）：

1. **按年级重排** —— `/timetable/bulk` 的**多班批量排课**：一次勾选 N 个年级班
   （B1/B2/B3/B4…）+ 同一科目 + 同一教师 + 同一周次 ⇒ 生成 N 组课时，**时间自动错开**
   （第 i 个班 = 首班时段 + i × 每班顺延；默认顺延 = 一个课时长度，另可填分钟覆盖）。
   ⚠ §18.2 的技术判据：**不能写脚本把一条合班课时复制成 N 条** —— 基座
   `openeducat_timetable` 的 `check_timetable_fields` 有**教师维硬约束**
   （同一 `faculty_id` 时间重叠直接抛 `ValidationError`），第 2 条起全部被拒，
   会留下「4 个年级只排上 1 个」的**半截数据**。**必须错开。**
2. **停用旧合班课时** —— `GET /timetable/batch/<id>/deactivate`（只读确认页）
   → `POST /timetable/batch/<id>/deactivate/confirm`（执行）。
   实现 = `edu_schedule/models/session_ext.py` 的
   `OpBatchGradeSplit.deactivate_batch_sessions`：`state='cancel'`，**不删行**；
   带二次确认 + `edu.audit.log` 留痕（动作名「课节批量停用」）。

**谁承担风险**：

| 风险 | 承担者 | 现有护栏 |
|---|---|---|
| 排错班 / 排错时间 | 教务 | `/preview` 落库前逐条列出（时间·科目·班级·教师·重叠维度），四查预检红格 |
| 一位老师同一时刻要给 4 个班上课（假课表） | 系统 | `/create` 写库前**再查一次**，**有一条冲突就整批拒绝**（不写一半）；同批内互相冲突也查（后建的班把先建的课时当既有占用） |
| 停用停错了班 | 教务 | 只读确认页列出「将停用 N 节 / 时间范围 / 科目分布 / 受影响的人」，必须**再勾确认框再提交**；不删行 |
| 学生课表看不出停用效果 | —— | 已在 `edu_portal/controllers/scheduling.py` 补 `('state','!=','cancel')`（§18.3 能力 B 的前置） |

**怎么回退**：

1. **排课回退** —— 新建课时可逐节改/删（后台 `op.session` 列表），或整批停用。**可逆。**
2. **停用回退** —— ⚠ **没有一键反向操作**。回退只有两条路：
   ① 后台 `op.session` 记录表单把 `state` 从 `cancel` 改回 `draft`
   （`state` 是普通 selection，取值 `draft/confirm/done/cancel`，可写）；
   ② `psql` 手改（**不推荐**：绕过 ORM 就没有 C-1 的字段级留痕）。
   **这一条要写进操作单，并且要靠 §5.0 的备份兜底。**

**能不能达成用户诉求：能 —— 但有一个前提必须单独守住。**
甲把课排到**年级班**上，而课表按**学生档案班**匹配 ⇒ **只有当「排课班 = 学生档案所在班」时学生才看得见**。
本地库唯一在读的档案挂在 batch 8（预备科演示批），它不属于 A/B 系任何年级班
⇒ **就算甲做完了，那唯一一位在读学生这周仍然是 0 节。**
所以甲之外**必须**同时确认「学生档案里那个 `batch_id` 指向的就是被排课的年级班」——
这属于**学籍数据**，不是排课功能（§7 第 2 条）。

### 乙（动模型加「教学班 ↔ 行政班」归属表）

**提案内容**：① 在 `op.batch` 上加父子/成员关系，或新建「教学班 ↔ 行政班」归属表；
② 学生课表口径从「档案班」扩成「档案班 ∪ 已批准科目所在教学班」。

**先说一个必须先讲清的事实：这个「归属表」在本仓已经有了 —— 而且不是表，是代码。**

`edu_schedule/models/session_ext.py` 的 `OpBatchGradeSplit._deactivate_composition`
**已经实现了「合班批 → 组成年级」的推导**：把 `op.batch.code` 按
「字母 1–2 位 + 数字串，数字串逐位展开」解析成单年级代号（`B1234 → B1/B2/B3/B4`、
`A123B234 → A1/A2/A3/B2/B3/B4`），再逐个按 `code` 反查真实班级。
§18.5 那张「生产合班批 → 组成年级」映射表就是它的产物，页面上**强制标注「推导，需人工确认」**。

**实测（`--section c` 的 C1）：本地 9 个合班批全部推导成功、unknown = 0**

    10  B1234     → B1、B2、B3、B4
    12  B34       → B3、B4
    13  B234      → B2、B3、B4
    15  A123      → A1、A2、A3
    17  A123B34   → A1、A2、A3、B3、B4
    18  A123B234  → A1、A2、A3、B2、B3、B4
    19  A123B1    → A1、A2、A3、B1
    20  A23B34    → A2、A3、B3、B4
    22  A23       → A2、A3

⇒ 乙的「加一张归属表」在**推导层是重复劳动**；真正缺的不是表，是**数据**（见 §4）。

**谁承担风险**：

| 风险 | 说明 |
|---|---|
| 口径分叉 | 课表从「一个班」变成「一个集合」，与 LMS `/my/courses`、校历 `/my/calendar`、ICS 订阅、考勤点名四处口径**必须同步**，否则同一名学生四个页面显示四份不同的课 |
| 推导 ≠ 事实 | `code` 是人手填的自由文本（§18.5 自己写明「推导值，供人工确认，**不得当事实用**」）。`A123B34` 这种跨系合班，解析结果的语义只有教务知道 |
| 连带改动面 | 至少三处要同改：学生分支 / `_role_batch_context`（停课归属）/ 家长分支；漏一处就会出现「课表有课但停课不灰显」这类对不上 |
| 性能 | 每名学生每次开课表多一轮 `batch_id in (...)` 的并集查询；集合大小随合班层级增长 |

**怎么回退**：纯读取口径改动 + 一张可留空的新表 ⇒ 回退成本低。
**风险不在回退，在「看起来做了很多、用户还是看不到课」**（见下）。

**能不能达成用户诉求：不能（单独做）。** 见 §4。

### 丙（最小止血：教务用现有多班批量排课重排）

**动什么**：**零代码**。教务用**已经上线**的 `/timetable/bulk` 多班批量排课，
把合班批上的课按年级各排一份（时间错开），旧合班课时**先不动**（或按需停用）。

**与甲的关系**：**丙 = 甲的第 1 步；甲 = 丙 + 第 2 步（停用旧课时）+ §18 的完整验收口径。**
只做丙不做甲：旧合班课时仍留在库里、仍参与冲突检测、仍会在「全校课表（只读）」视角下重复显示。

**谁承担风险**：教务自己。当前代码上，多班排课那层护栏（预览 + 整批拒绝）丙也享受得到。

**怎么回退**：新建课时逐节改/删，**可逆**。

**能不能达成用户诉求：能 —— 与甲同样的前提**（排到的班必须是学生档案所在的班）。

## 4. 乙的关键问题：139 节挂在「学生数 = 0 的合班批」上的课，加了归属表能自动到学生身上吗？

### 结论：**不能。** 差的不是「一张表」，是**三样东西同时缺位**。

#### 缺位 ①：那些「组成年级班」自己也一个学生都没有

`_deactivate_composition` 能把 `B34` 解析成 `B3 + B4`，但：

| 班 | 课节数 | 挂批学生数（`op_student_course.batch_id`） |
|---|---|---|
| B1（id 14，人文一年级） | 18 | **0** |
| B2（id 25，人文二年级） | 0 | **0** |
| B3（id 16，人文三年级） | 40 | **0** |
| B4（id 21，人文四年级） | 15 | **0** |

⇒ 把口径从「合班批」换成「它组成的那些年级班」，命中集合**仍然是空**：
**全库 17 个班里，有学生的只有 batch 8（1 条 running 档案）**，而 batch 8 不属于任何合班批的组成。

#### 缺位 ②：基座**自带的**「把课点名学生」的机制也是从班级派生的，所以同样救不了

`op.session` 上有一个**真实存在、stored** 的 `many2many` 字段
`student_ids` → `op.student`（表 `op_session_op_student_rel`）。
基座 `openeducat_timetable` 甚至**自带一条迁移**
（`migrations/19.0.1.1.0/post-migrate.py`）去回填它，注释写明理由：
企业门户的 RPC `('student_ids','in',student.ids)` 对空值会返回空。

**但它的回填口径是「按 `batch_id` 找学生」** —— 于是：

| 读数 | 值 |
|---|---|
| `op_session_op_student_rel` 行数 | **0** |
| 有 `student_ids` 的课节数 | **0** |
| 9 个合班批的课节里带 `student_ids` 的条数 | **0** |

而且 `edu_schedule/controllers/main.py` 的 `_create` / `_create_multi`
在**建课时就已经这么写了**：

    student_ids = request.env['op.student.course'].search(
        [('batch_id', '=', meta['ids']['batch_id'])]).mapped('student_id').ids

⇒ 对合班批，这句的搜索结果**恒为空**，`student_ids` 落成 `[]`。
**所以「加一层归属」若仍以班级为锚，结果与现状逐字相同。**
（`session_ext.py` 的 `_reminder_users` 也留着这条回退，注释里
「本地库 `op_session_op_student_rel` 为 0 行，不回退就会静默算成 0 人」正是同一件事的存档。）

#### 缺位 ③：要让课自动到学生身上，只能从**选课结果**反推 —— 那正是「按科目匹配」

真正的自动化唯一通路是：

    已批准科目（op.student.course.subject_ids）
      ∩ 该科目在某个班上的排课（op.session.subject_id）
      → 学生的课表

而这**不是「教学班 ↔ 行政班归属表」**，是**「科目 ∩ 排课」** ——
恰好就是 B1 诊断 §7 的 R3 选项②：「课表口径改为 `subject_ids ∩ batch 排课`」。

⚠ 但档案里的科目与 139 节课的科目**是两批**：本地唯一在读档案的科目是
`[46] 选修课程`，它**在 `op.session` 里一节都没有**（§6 的 B 段读数）。
⇒ **两批科目在本地库的交集是 0。**

#### 所以乙「还差什么」——逐条

1. **差数据**：学生必须真的挂在（或选到）那些有课时的班上/科目上。现在全库只有 1 条在读档案，
   它在 batch 8（演示批），而 batch 8 的课时**在 2026-09-18 就全部结束了**（本周 0 节）。
2. **差一条真正的口径决定**：「课表表达什么」—— 是「教务给这个班排了什么」还是
   「这名学生要上什么」。乙把它改成后者的一部分（行政班并集），但**没有引入科目维度**，
   所以对「选课后课表出现该科」这个诉求**结构上无解**。
3. **差一致性**：口径一改，LMS / 校历 / ICS / 考勤四处必须同改。
4. **差「写什么」**：若连「没有排课的科目」也要出现在课表里，就必须在课表侧**渲染占位行**
   （「该科尚未排课」），否则学生看到的仍是空课表 —— 那是另一个产品决定，乙没有覆盖。

> **一句话**：乙能解决的是「学生有多个行政班时课表只显示一个班」这个**潜在**缺陷
> （B1 诊断 §6.4 记的那个），**解决不了**「选好课之后课表里要出现他的每日课程」。
> `scheduling-overhaul-design.md` §18.4 也把 ②（班-班归属）**降级为备选**、
> 并写明「本期不立项，出现跨系合班且教务不愿按年级重排时再评估」——本节的实测**支持**这个降级。

## 7. 推荐与理由

### 推荐：**丙（当天可做，最小止血）+ 甲（按 §18 走完，真正的解）**；乙**不立项**

逐条理由：

1. **用户的诉求是「课表里有课」，不是「课表读得对」。**
   本地实测：唯一在读学生的档案班本周 **0 节**、9 个合班批的 139 节课**挂着 0 个学生**。
   ⇒ 现在无论怎么改**读取口径**，学生页面都是空的。**乙改的正是读取口径。**
2. **甲/丙是唯一同时解决「有课」和「到得了学生」的路**：把课排到年级班后，
   「排课班」与「学生档案班」**重新对齐**（§18.4 已写明这一点）；
   乙则要求「学生同时属于多个班」，而本库连一个学生都没挂上。
3. **甲的成本已经付过了**：§18 的两件能力**本期已实施**（§18.7 落点逐条在册）。
   甲现在是**操作任务**，不是开发任务。本文件 §6 的干跑就是那两件能力在真实数据上的可运行证明（13/13 PASS）。
4. **乙在本库当前数据下收益为 0**，成本却是四处口径同步 + 一条自由文本推导规则被提升为事实源。
   §18.4 已把它降级为备选；本节的实测**支持**这个降级。
5. **甲有一处必须单独守住的前提**（不是甲的功能缺陷，是数据纪律）：
   **排课的目标班必须是学生的档案班**。本库唯一在读档案挂在 batch 8（演示批），
   它不在任何 A/B 系年级班里 ⇒ 甲做完，那一位学生本周仍是 0 节。
   这一点必须作为**独立验收项**写进操作单，不能被「排完课了」的绿色掩盖。

### 为什么不是「乙 + 甲一起做」

乙要在 `scheduling.py` 的学生分支 / `_role_batch_context` / 家长分支三处同时改口径，
而这三处正是甲要依赖的「停课灰显」「课表可见性」判据。
**先甲后乙**可以在甲落地后拿到「单班口径下学生确实看得到课」的干净基线；
反过来（先乙）会把两个变量的读数混在一起，出问题时分不清是排课没做还是口径写错。
