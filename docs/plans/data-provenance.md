#### G1 更正：`check_english.py` **扫不到**注册页（2026-09-12 实测）

原文写「会被 `check_english.py` 的属性扫描命中」—— 机制对，**但那条路由根本没被扫**。实测证据：

```bash
# 门禁扫的是 /web/register（t4 改名前的旧路径）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' 'http://localhost:8069/web/register?db=edu19'
#   → 302 http://localhost:8069/register        ← 门禁拿到的是 302 响应体（里面没有任何属性）

# 真正有表单的页面，却不在门禁路由清单里
curl -s 'http://localhost:8069/register?db=edu19' | grep -oE '(placeholder|title|aria-label|alt)="[^"]*"'
#   → placeholder="you@example.com" ／ aria-label="Logo of 永约学坊" ／ aria-label="Main" ／ aria-label="Mobile" …
```

**两条机制叠加导致漏扫**：
1. `scripts/check_english.py` 的路由清单里是 **t4 改名前的 `/web/register`**，而非 `/register`（`/login` 已更新，注册这条没跟上）；
2. 该脚本取页面用 `allow_redirects=False`（:`379`、:`612`）→ **不跟随重定向**，302 的响应体里没有任何可见属性。

⇒ **注册页整页从未被可见英文门禁扫过。**

**炸开半径已查实（2026-09-12 全量核对）**：三份清单（PUBLIC/PORTAL/TEACHER_ROUTES）去重共 **86 条路由**，
逐条实测 302 的**跳转目标**（指向 `/web/login` = 需登录，正常；指向友好路径 = 改名替身）→
**重定向替身只有 `/web/register` 一条**，即**唯一被漏扫的就是注册页**。

**佐证这是「漏了一条」而非「系统性腐坏」**：t4 同时改了三条路径，另两条**都更新到位**了 ——
`/web/login`→`/login`（清单里已无旧路径）、`/openeducat/apps_menu`→`/apps`（旧路径不在清单、新路径在）。
⇒ **人手工维护清单时，「三条改对两条」是常态** —— 这也正是下面那条建议（加「路由必须返回 200」的断言）的理由：
**别指望人每次都记得，让机器在漏的时候就红。**

**与 t10 发现的邮件面盲区同族**：门禁扫的是面 A，真实面在 B —— 而且这类**不是"没检查到"，
而是"检查本身走错了面"**，输出仍是干净的绿。

### 8.1 授权与最终口径

用户的原始指令是「把所有的学费都改成统筹费」。队长最初设的「公开页事实性文案先交用户确认」
闸门针对的是**事实本身**（数字 / 日期 / 联系方式），**术语改名不改变任何事实**，
故 2026-09-12 队长明确授权按下列口径直接应用全部 12 处：

| 类别 | 处数 | 最终改写 | 说明 |
|---|---|---|---|
| 真实收费项（#6 #8 #11 #12） | 4 | 「学费」→「统筹费」 | 与教务系统收费科目同义，直接改名 |
| 「不收取学费」（#2 #3 #4 #5 #7 #9 #10） | 7 | 「不收取学费」→**「不收取统筹费」** | 用户要的是**术语统一**；「不收取统筹费」语义自洽（确实不收这笔费用），且与家教学院那笔「统筹费 100 元/学分」用同一个词。**不用「学费（统筹费）」写法**——那样仍含「学费」，术语门禁永远过不了 |

### 9.1 切换前实测

| 项 | 值 |
|---|---|
| `res_company` | 永约学坊（id=1），currency = **USD（$）** |
| CNY | id=6，symbol ¥，**active = false**（未激活） |
| `edu.fee.bill` | 2 行（【演示】2026 春季统筹费 12000、【演示】教材资料费 300），均挂 USD |
| `edu.fee.payment.currency_id` | related 到 `bill_id.currency_id`，无需单独迁移 |
| `account.move` / `account_move_line` | **0 行** → 无会计分录，切币种不涉及汇率重估 |

### 9.2 执行步骤（幂等，可重跑）

1. `res.currency` **必须带 `with_context(active_test=False)` 才能搜到未激活的 CNY** ——
   该模型有 `active` 字段，ORM 默认加 `active_test` 过滤。
   **踩过的坑**：不带该 context 时 `search` 返回空集，随后写
   `company.currency_id = cny.id` 得到 NULL → `NotNullViolation: null value in column "currency_id" of relation "res_company"`，
   整事务回滚（数据未受损）。**看到这条报错就是这个原因，不是权限问题。**
2. `cny.active = True`。
3. `res_company(1).currency_id = cny.id`。
4. 存量 `edu.fee.bill` 的 `currency_id` USD → CNY（**不换算数字**：12000/300 本就是人民币口径的演示金额，
   原挂 USD 属标记错误，属纠正而非折算）。

### 9.3 切换后实测

`永约学坊 | CNY | ¥ | active=true`；2 张账单与全部流水均为 CNY；
`/my/fees` 与 `/ledger` 渲染为 `¥12000`、`¥12200`、`¥300`（此前为 `$…`）。
**证明 t5 的「按 res.currency 渲染」改造有效**：模板未改一行，只切了币种，符号自动跟着变。

### 9.4 影响面与回滚

- **影响面**：所有未显式指定 `currency_id` 的 Monetary 字段默认取公司币种（如 `edu.fee.bill.currency_id` 的 default）；
  显示符号与小数位随之变化。本次因 `account.move` 为 0，无历史凭证需要重估。
- **回滚**（一条 SQL 即可）：
  ```sql
  UPDATE res_company SET currency_id = (SELECT id FROM res_currency WHERE name='USD') WHERE id = 1;
  UPDATE edu_fee_bill SET currency_id = (SELECT id FROM res_currency WHERE name='USD');
  UPDATE res_currency SET active = false WHERE name = 'CNY';
  ```
  回滚后 `-u edu_portal` 或重启 web 使缓存失效即可。
- **生产**：需要用户确认后才执行；建议先备份 `edu19`（`pg_dump`）再切。
