## 3.4 分层验收：门禁全绿 ≠ 全绿（README 级结论）

本轮最容易被误读的一点：**t9 的七项独立验证全绿，并不等于所有需求项都闭合**——因为两者测的不是同一层：

| 层 | 谁来测 | 覆盖内容 | 盲区 |
|---|---|---|---|
| **可观测面** | 门禁（check_english / check_odoo_trace / 路由矩阵 / 截图 / 首页高度 / 数据不变量） | 路由可达、英文残留、品牌痕迹、性能指标、数据根因 | **审计完整性、授权边界、业务规则一致性** |
| **审计完整性** | 只能靠**交叉评审读代码 + 造数据实测** | 改分是否全路径留痕、批量是否逐条可追溯 | 任何门禁都测不出来 |
| **授权边界** | 同上 | 教师能否改非本人课程的成绩、批量入口是否与单条同门禁 | 同上 |

**门禁的「归因策略」有三种，可信度不同**（方法论文档 `docs/dev-workflow.md` 有完整表）：
· **结构推导**（AST + 导入序）→ 可直接给 `文件:行号`，能据以动手（`check_view_xpath` 规则 7）；
· **子串匹配** → **只能当线索**，必须回渲染实测确认（`check_english` 的「来源」列 —— 这条已骗过三个人）；
· **不做归因** → 只报渲染证据与样本，由人定位（`check_odoo_trace`：与其给一个可能错的出处，不如只给证据）。

**两条口径纪律（t9/t13/t34 落地）**：
1. **"门禁全绿"必须写在它的口径里**，不外推成"业务/审计也全绿"——t9 七项只覆盖可观测面；
2. **claim 与证据要同级**：t7 的「改分唯一入口、全部留痕」是 **claim**，只有"写一次 → 查留痕表 → 字段正确"这种**行为级验证**才配得上它。
   （t34 已修 + verifier 行为级复核通过：`HIST id=11 source=backend old=92 new=93`，还原后 `LEFTOVER=0 MARKS=92`；并已固化为可复跑冒烟 `tests/smoke/audit_completeness_smoke.py`，见 t39。详见 `docs/plans/ux-v3-verification.md` §17。）

**另一条同源原则：互补 ≠ 并集完备。** 两个门禁合起来覆盖 `文本节点 + title/placeholder/aria-label/alt/content`；
