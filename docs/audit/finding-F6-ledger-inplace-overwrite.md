# 发现 F6（工具隐患）：合并台账「就地覆写」导致同文件名的破坏性随时间漂移

- 发现人：data-eng 指出，verifier 复核认同并登记
- 日期：2026-09-17
- 严重度：**medium**（不影响已迁移数据，但使"回滚判据"不可靠、易生误操作）
- 归属建议：t12（data-eng 已认领）

## 1. 问题

`scripts/merge_checkins.py` 每次 `--apply` 都会把
`scripts/migrations/ledger/checkin-merge-latest.jsonl` **就地重写**为"本次运行"的内容。
⇒ **同一个文件名，在不同时间点的破坏性完全不同**：

| 时刻 | latest 的内容 | 此时跑 `--rollback` 的后果 |
|---|---|---|
| 首跑后 | 含 `created=8` 明细 | 会**真删** 8 条（若它们仍在） |
| 幂等复跑后 | `created=0`（全 skip） | **安全 no-op** |

这正是 verifier 本次误触的**根因**：以为拿的是"带 created 的那版"，实际语义随时点漂移。
（真正产生写入那次的快照保留在 `checkin-merge-applied-ledger.jsonl`。）

## 2. 建议（data-eng 提，verifier 认同并补充）

1. **回滚只认"带 created 的那一版"，且先复制成临时文件再喂给 `--rollback`**；
   不要直接拿 `latest` 当回滚输入。（verifier 第二次就是这么做的，安全闸测试零改动。）
2. **要留档历史批次，用 `checkin-merge-applied-ledger.jsonl`，不要动 `latest`**。
3. **治本**：让脚本**不覆写**——每次 `--apply` 落一个**带时间戳的新文件**，
   `latest` 仅作**符号性指向**（或记录"本次指向哪个批次"），
   从根本上消除"同文件名不同语义"。
4. 附带：台账里应显式记录**输入版本 / 运行模式 / 是否含 created**，
   使"这份台账能删什么"可被机械判定，而非靠人回忆。

## 3. 影响面

- **数据**：无影响（本次误触删除数为 0，4 条 note 已 `--apply` 补齐，账目闭合）。
- **流程**：任何按 `latest` 做回滚演练/复核的人，都会遇到"判据不可靠"；
  这条比"记得用构造台账"更根本——因为后者依赖人的记忆，前者是机制缺陷。
