## ~~Q-01「共 N 门科目已生效」这个数，等于真的建了几条在读吗？~~ **已结：不是缺陷（第 83 轮）**

> **结论**：通知报的数**就是**写进档案的那一份 —— 两处用的是**同一个函数**，不可能漂：
>
> ```python
> # models/registration.py
> line 146:  n = len(self._subject_payload())      # 通知正文里的「共 N 门」
> line 192:  subject_ids = rec._subject_payload()    # action_enroll_approve 真正写进 op.student.course 的
> ```
>
> `_subject_payload()` 的 docstring：「注册单科目并集（compulsory ∪ elective，去重升序）」。
> 审批时是**整体覆盖** `subject_ids`（docstring：「找到则更新档案并整体覆盖 subject_ids」）⇒
> 「在读 1 门」数的是 **`op.student.course` 行数**，「14 门科目」数的是**挂靠的科目数** ——
> **两个数都对，量的不是一回事**。
>
> **⚠ 我在第 82 轮的判断是错的**：当时写「只能真去批一张才能验」——其实**读代码就够了**。
> 这是一次「证据就在手边，我却去设计一个会动真实数据的实验」的教训。
>
> 顺带说明：今天库里该档案的 `subject_ids` 只剩 1 门（「选修课程」），而通知里是 14 ——
> 那是因为那条通知是**更早一次数据库状态**的旧消息，之后档案被别的动作覆盖过。
> 但**机制上**两者同源，所以通知在发出的那一刻是准的。

### 原始记录：「共 N 门科目已生效」这个数，等于真的建了几条在读吗？

**现象**：学生私信里有一条系统通知（`models/registration.py:147`）：

```
【选课通知】您的选课申请 SR0023（预备科 · 预备科 · 2026级【演示】）已通过，
共 14 门科目已生效，可在「我的课程 / LMS」中开始学习。
```

而学生自己的页面显示 **在读 1 门**（`/my/courses`），数据库里也确实是：

```
学生 5 的 op.student.course 行数: 1   按状态: {running: 1}   按课程: {预备科: 1}
```

**已查到的**：
· 通知里的数来自 `n = len(self._subject_payload())`；
· `_subject_payload()` 的 docstring 写明是「**注册单科目并集**（compulsory ∪ elective，去重升序）」——
  即**这张注册单上列了多少门**，不是学生最终在读多少门；
· 第 55 轮修过同一个「14 vs 1」的混淆（当时是 `/my-courses` 卡片拿专业科目总数当在修数）。

**为什么还不能定性**：
· 那张 `SR0023` 在库里**已经查不到**（`search([('name', '=', 'SR0023')])` 为空）⇒ 这条通知是
  **更早一次数据库状态**留下的旧消息，不是当前行为的产物；
· 要判定「通过一张 14 门的注册单，到底建了几条在读」，只能真去批一张 ——
  而审批会**真实移动学生班级**（审批页自己写明「通过后该生将从原班的点名表与评教名单中移除」），
  第 76 轮已决定**不为测试触发它**。

**需要谁定**：用户（是否值得为此单开一次可回滚的演练库来验）。

## Q-03 教务宫格上的「打卡统计」是死卡（1 张）

**现象**：第 87 轮新立的 `scripts/probe_home_cards.py`（四个角色首页宫格逐卡点进去）实测：

```
DEADCARD backoffice[打卡统计] /checkins/stats → 被弹回 /my/home
```

**已查到的**：
· `/checkins/stats` 的守卫自己写着「学生回自己的打卡页；**其余内部用户回门户首页**」
  （`edu_life/controllers/life.py:469`）⇒ **教务被弹回是有意为之**，所以问题在**卡片**；
· 但教务的宫格**不走** `_home_categories`（那是学生/家长那套卡片源）—— 我一度在
  `_home_categories` 里加了「没有 faculty 绑定就不出这张卡」的判断，实测**毫无效果**，
  查库确认 `backoffice@local` 确实 **faculty 绑定 0 条** ⇒ 说明它根本没经过那条代码路径，
  **那段判断是死代码，已删除**。

**缺哪一步证据**：教务首页宫格的卡片源在哪（`_home_categories` 之外的那一套），
以及「打卡统计」这张卡该不该给教务 —— 是**藏掉卡片**还是**放行教务**，取决于业务意图。

**当前处置**：探针已接进 `check_all`，用本仓既有的「已知项」模式（`KNOWN = 1`）——
**超过 1 条才判红** ⇒ 新混进一张死卡会立刻报警，而这条已知项不会让门禁永远红着。

**需要谁定**：用户（教务要不要看打卡统计）。

## Q-04 `/online-exams` 对**未登录游客**公开（第 107 轮实测，登记待裁定）

**怎么发现的**：学生的导航里「考试」指向 `/online-exams`。走考试闭环时注意到它**用的是公开站外壳**
（页头是「学院概况 / 专业设置 / 招生信息 / SCRTS 校刊 / 登录 …」），于是用**游客态**（未登录）直接访问：

```
游客 /online-exams → 200，页面渲染出：
  在线考试 ｜ 阶段考一 · 小要理问答【演示】 ｜ 小要理问答 · 2026/08/30
           ｜ 小要理问答 · 第一学期 总评 ｜ 小要理问答 · 2026/06/23
           ｜ 基础信仰 · 第一学期 总评 ｜ 基础信仰 · 2026/06/23
含「王小明」= False ｜ 含「预备科」= False ｜ 页面无任何分数数字
```

**泄露面的准确边界**（这是本轮真正的新信息 —— 此前只有「它公开吗」这个问题，没有「公开了什么」）：

| 公开 | 不公开 |
|---|---|
| 考试名称（阶段考一 / 学期总评）、考试日期、课程名 | 学生姓名、班级、任何分数 |

**为什么不能我自己改**：这属于「**公开还是隐藏**」的产品决定（公开的考试日程对招生季可能是**卖点**，
也可能被视为**内部安排外泄**）。校长定的规矩是「**先修问题，不擅自改版**」，且本项目已多次登记过
「公开表单 / 公开页」类待裁定项 ⇒ **只登记，不动**。

**要动的话，两个方向**：① 保持公开（若考试日程本就是可公开的招生信息）；
② 改成 `auth='user'` 并让游客跳登录（若认为日程属内部安排）。
⚠ 无论选哪个，都要注意：**学生的导航「考试」正指向这里** ⇒ 改权限会同时影响学生入口。

## Q-02 还原动作本身会触发通知

第 71/72 轮的探针在还原数据时用 `sub.write({'state': 'submit', 'marks': 0.0})`，
而 `models/assignment.py:6` 的钩子是「state 流转到 accept/reject/change **或 marks 变更** → 站内信」，
⇒ **还原也给学生发了一条**「已批改（得分：0.0）」。

这不是产品缺陷（真实系统不会把已批改的作业退回待批阅），但它是我**探针卫生**上的疏忽：
以后写「先改后还原」的探针，要意识到**还原本身也是一次业务写**。
登记在此，供下一个人写同类探针时避坑。
