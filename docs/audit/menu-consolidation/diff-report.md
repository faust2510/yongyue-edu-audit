### 1.1 C 口径（可见叶子）三处「同源不同值」的对账 —— 差异已定位到**口径定义**

本表 C 的数字来自 **ORM 快照**：`scripts/menu_baseline.py` 里「可见集合 ∩（有 action 且无子菜单）」。
采集时刻：前 2026-09-17 03:35:05 / 后 2026-09-17 06:25:18（取值自两份快照的 meta.generated_at_utc）。
| 口径 | 定义 | admin | backoffice | faculty |
|---|---|---|---|---|
| 本表 C（ORM 快照） | 可见集合里“有 action 且无子菜单” | 306 | 153 | 65 |
| 前端 load_menus（带 action 的节点） | 同一份前端数据里 `actionID/action` 非空的节点 | 294 | 153 | 62 |
| 验证方口径（排除根） | 节点 `id != appID` **且** `children` 为空 | 279 | 140 | 53 |

**已定位的差异（逐项可复算）**：
1. 验证方与本表的差 = **根节点不算叶子**。本表把“根 + 有 action + 无子项”的节点也计为叶子，
   实测全库只有 **1 个**这种节点：**`608 资料下载`**（admin 与 backoffice 的可见集里有它、faculty 没有）。
   ⇒ admin 294−279=**15**（14 个带 action 的根 + 608）、backoffice 153−140=**13**（12 + 608）、faculty **53=53**（无此类节点）。
2. 本表(ORM) 与前端(294/153/62) 的差 = admin **12** / backoffice **0** / faculty **3**，
   方向也不总是同向（部分节点 ORM 算叶子、前端不算，另有部分反之），**该差因未证**；
   已知的合理来源是前端会额外过滤 `base.group_no_one` 等技术菜单、以及根/层级的判定差。

> **验收只以 B 口径（可见根数）为准；C 仅供旁证。**
> 引用 C 时必须同时写清“用哪种口径 + 采集时刻”，否则同一个角色会出现 279/140/53、294/153/62、306/153/65 三套数字。
