# 附件字节抢救（B15）—— 方法、实测与独立复现（2026-10-01）

> 记录人：loss-ledger（task-3 续作）｜执行：队长（2026-10-01，新机 /opt/edu-app）｜**独立复现：loss-ledger**
> 目的：把「8/30 快照里有多少附件字节还在本机」这件事做成可复跑的账，而不是一句印象。

## 1. 结论（一句话）

**8/30 快照有 710 条 `ir_attachment` 带实体（`store_fname` 非空，540 个唯一 blob）；本机 Mac filestore 命中 157 条（91 个唯一文件）。**
**这 157 条全是平台资源与头像，没有一件是校方上传的业务资料** —— 因为 8/30 快照里 `edu*`/`op.*` 的附件本来就是 **0 行**。

## 2. 三个口径，别混

| 口径 | 数字 | 分母 |
|---|---|---|
| 快照里有实体的附件**行** | **710** | 8/30 dump 的 `ir_attachment` |
| 其中唯一 blob 数 | **540** | 同上（`store_fname` 去重） |
| **本机命中（行口径）** | **157** | 710 |
| **本机命中（唯一文件口径）** | **91** | 540 |
| 新机上现在「能找到字节」的行 | **186**（唯一 98） | 新机 709 行 |

> `store_fname` = 内容的 sha1（**路径自带 `xx/` 两级前缀**），所以**多行可以指向同一个 blob**：
> 「157 行」= 有多少条挂接的字节还在；「91」= 实际搬了几个文件。**两个数都对，口径不同。**
> 新机 186 > 157：升级/启动时 Odoo **又生成了新附件**（编译资产、视图图片）并写入 filestore ⇒「现在存在」≠「抢救来的」。

## 3. 可复跑方法（逐字）

### 3.1 从 dump 抽 `store_fname` 列表（不还原库）

```bash
env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY scp ~/Documents/edu19-backups/edu19_post_cleanup_0830.dump prod-host:/tmp/snap0830.dump
env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY ssh prod-host \
  'docker cp /tmp/snap0830.dump edu19-prod-db-1:/tmp/snap0830.dump && \
   docker exec edu19-prod-db-1 pg_restore -a -t ir_attachment -f - /tmp/snap0830.dump > /tmp/att.tsv'
# /tmp/att.tsv -> 1006 行（971 条数据行 + COPY 头 + \.）
```

解析器（本机 `python3 /tmp/parse_att2.py`，逐字逻辑）：找 `COPY public.ir_attachment (` 行 → 取列名定位 `store_fname` 的下标 → 逐行 `split('\t')` → 跳过空值与 `\N`。

```text
all= 710  unique= 540
```

### 3.2 与本机 filestore 对拍（本机 Mac）

```bash
FS=data/web/filestore/edu19          # 本机克隆的 filestore，192 个文件
while IFS= read -r f; do [ -n "$f" ] && [ -f "$FS/$f" ] && echo "$f"; done < /tmp/sf_dump_all.txt > /tmp/hits_from_dump.txt
wc -l < /tmp/hits_from_dump.txt           # 157  ← 行口径
sort -u /tmp/hits_from_dump.txt | wc -l   # 91   ← 唯一文件口径
```

### 3.3 结果与交叉核对

```text
rows_present=157

```

### 3.4 上传到新机并修属主

```bash

# 新机 filestore 文件数 91 -> 265（含 Odoo 运行时生成的资产）
```
