## 0. 一句话主张

**把「填表」和「后果」放在同一屏的两栏里：左栏填、右栏实时说「所以会生成什么」。
服务端的「先预览、确认后才写入」一步不删、一步不省 —— 右栏只是把原本要等到预览页才知道的
结构性后果（几节、首末哪天、每周几点的哪个班）提前到输入的同时。**

真正要治的病不是「控件多」，而是**决策与后果隔了一次提交**：
用户填完 12 个字段、滚 1200px、点一次提交，才知道自己填的到底意味着什么。
把后果搬到右栏，是让「一屏之内看到全部决策与后果」成立的最短路径。

### 1.2 结构复核：基线 7 条**全部复现**，另加 3 条我自己发现的

baseline 的 7 条我逐条在 DOM 与截图上复现了，不重复。**新增 3 条它没写的**（这 3 条直接决定了我的设计）：

**新增 A ——「返回修改」会把用户填的 12 个字段全部丢光。**
预览页的返回链接是 `<a href="/timetable/bulk">`（[templates.xml:717](custom_addons/edu_schedule/views/templates.xml#L717)），
是一条**裸 GET**；`_render_bulk()` 只接受 `error` 等几个键
（[main.py:133–137](custom_addons/edu_schedule/controllers/main.py#L133-L137)），**不回填任何字段**。
实测：填 13 个字段 → 提交 → 得到预览页 → 点「返回修改」→ 表单**全空**。
⇒ 既有安全设计的代价（先预览）被转嫁成了**重复劳动**：参数填错一个，全部重填。

**新增 B —— 校验失败也丢字段。**
我故意不选班级提交，服务端 `_plan_ctx` 返回「请选择班级。」
（[main.py:360–361](custom_addons/edu_schedule/controllers/main.py#L360-L361)），
再用 `_render_bulk({'error': error})` 重渲染 —— **这一次连预览页都没到，字段照样全丢**。
实测证据：重渲染后 `input[name=start_date]` 的值回到空串，「课程」下拉回到「— 请选择 —」。

**新增 C —— 两个班级字段的优先级，页面上一个字都没说。**
`_resolve_batch_ids()` 只读 `batch_ids`（[main.py:541–562](custom_addons/edu_schedule/controllers/main.py#L541-L562)），
**从不读 `batch_id`**；只要勾选了任意一个复选框，单班下拉 `batch_id` 就被**完全忽略**。
页面上没有任何一处告诉用户这件事 —— 用户很可能「上面选了班 + 下面勾了一个班」，
以为两个一起排，实际**只排勾选的那个**。

## 2. 信息架构

### 2.1 屏面分区

页面从「一张 1042px 的长卡」改成 **三层**：

```
┌ 第 0 层：页头（通栏，不参与两栏）───────────────────────────────┐
│ 家 / 周期排课                                                    │
│ 周期排课（批量生成课表）                                          │
│ 一句话导语                                                       │
│ [结果提示条]（生成成功后才有）                                    │
│ [停课日提示]（有停课日才有，压成一行 + 「查看全部」）              │
├ 第 1 层：工具切换（通栏）─────────────────────────────────────┤
│ [ 生成课表 ]  [ 停用课时 (11) ]        ← 两个工具，一眼是两个      │
├ 第 2 层：两栏（决定成败的一层）────────────────────────────────┤
│ ┌ 左栏 58%（可滚动）──────────┐  ┌ 右栏 42%（sticky）─────────┐ │
│ │ ① 上什么课                  │  │ 将会生成（实时）            │ │
│ │ ② 什么时候上                │  │  ├ 还差几项                │ │
│ │ ③ 排多久                    │  │  ├ 四组决策回显             │ │
│ │ ④ 给哪些班                  │  │  ├ 结论（N 节 / 首末）      │ │
│ │                            │  │  ├ 冲突与停课日：还没查      │ │
│ │                            │  │  └ [预览并确认] ← 吸底       │ │
│ └────────────────────────────┘  └───────────────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

**关键约束（决定落地正确性）**：**右栏必须物理上在 `<form>` 内部**。
现在的 `<form>` 就是那张卡（[templates.xml:83–84](custom_addons/edu_schedule/views/templates.xml#L83-L84)），
主按钮在 `</form>` 之前（[261–263](custom_addons/edu_schedule/views/templates.xml#L261-L263)）。
把主按钮搬到右栏时，若右栏在 `<form>` 外面，**提交会少掉全部字段**。
做法：`<form class="row g-3">` 作为两栏的网格容器，左 `col-lg-7`、右 `col-lg-5`，
按钮留在 `<form>` 内。**不使用 `form="…"` 属性**（本仓无此先例，且在该页会增加不可预期性）。

### 2.2 左栏：四组卡片（成组、可折叠）

分组**按用户的心智顺序**，不按后端字段顺序。四组的名字就是用户会问的四个问题：

| # | 组名 | 装什么（对应现有字段） | 默认 | 标题右侧常显摘要 |
|---|---|---|---|---|
| ① | **上什么课** | `course_id`+`new_course_name`、`subject_id`+`new_subject_name`、`faculty_id`、`classroom_id` | **展开** | 预备科 · 小要理问答 · T14 教师乙 · 不指定教室 |
| ② | **什么时候上** | 上课时间（`timing_id` / `custom_begin`+`custom_end`）、`weekday` | **展开** | 每周一、周三 08:00–09:30 |
| ③ | **排多久** | `start_date`、`end_date`、`parity`、`week_ranges` | **展开** | 09-01 → 10-31 · 每周 · 全部周 |
| ④ | **给哪些班** | `batch_id`（单个）、`batch_ids`（多个）、`stagger_minutes` | **展开** | 1 个班：A1+A2+A3合班 |

**为什么 ③ 不再把「周次范围 / 循环方式」单列：** 现在这两项和日期是分开的三块
（[220–229](custom_addons/edu_schedule/views/templates.xml#L220-L229) / [230–249](custom_addons/edu_schedule/views/templates.xml#L230-L249) / [250–259](custom_addons/edu_schedule/views/templates.xml#L250-L259)），
在 `col-md-4 / col-md-2 / col-md-3 / col-md-3` 里留出一个空列，视觉上像「漏了一块」。
它们四个回答的是同一个问题（「排到什么时候、隔多久一次」），合并成一组后语义完整、也消掉了空列。

**折叠 ≠ 隐藏**：每一组折叠后，标题右侧**直接显示当前值**（上表最后一列）。
用户不展开也知道自己选了什么 —— 这是「默认折叠」在本仓能被接受的前提。
（本仓既有先例：`edu_life` 打卡 streak / 周记三态 的收起态都带摘要。）

**④ 组的具体形态（这一组是「18 个复选框」的正解）：**

```
▾ ④ 给哪些班                              1 个班：A1+A2+A3合班
    班级 *              [ A1+A2+A3合班 ▾ ]         ← 单班，永远可见
    ▸ 一次排多个班（各年级分开排）                  ← 折叠，默认收起
      ┌ 展开后 ────────────────────────────────┐
      │ ☑ A1+A2+A3合班   ☐ A123+B1合班  …      │  ← 17 个班，**不带代号**
      │ ☐ 人文一年级     ☐ 神学一年级   …      │
      │ 每个班往后错开（分钟） [ 留空 = 一节课 ] │
      │ ⓘ 勾了班就以勾选的为准，上面的「班级」不生效 │
      └────────────────────────────────────────┘
```

- 默认只看见**一个**下拉；17 个复选框收进一个折叠块 ⇒ 首屏立刻空出来；
- 代号从**屏幕上消失**，改为：`title` 提示 + 「选多个班」区里的**搜索关键字**（`data-code`）；
- 补上现状缺的那句优先级说明（§1.2 新增 C）。

### 2.3 右栏：将会生成（三段式，**这是本方向的核心**）

```
┌ 将会生成 ──────────────────────────────────┐
│ 还差 3 项：科目 · 教师 · 上课时间              │  ← 第 1 段：进度
├────────────────────────────────────────────┤
│ 上什么课    预备科 · 小要理问答 · T14 教师乙    │  ← 第 2 段：决策回显
│ 什么时候上  每周一、周三 08:00–09:30          │     （与左栏四组一一对应）
│ 排多久      09-01 → 10-31 · 每周 · 全部周      │
│ 给哪些班    1 个班：A1+A2+A3合班              │
├────────────────────────────────────────────┤
│ 共 17 节                                    │  ← 第 3 段：后果
│ 首节 09-07 周一 · 末节 10-28 周三             │
│ ▸ 展开 17 个日期                             │
├────────────────────────────────────────────┤
│ ⚠ 冲突与停课日：**还没查**                   │  ← 第 4 段：诚实区
│   点下面的按钮，系统会逐条检查并告诉你会撞上    │
│   什么；有冲突就一节都不会写入。               │
├────────────────────────────────────────────┤
│ [ 预览并确认 ]                      ← 吸底    │  ← 主操作常驻
└────────────────────────────────────────────┘
```

**第 4 段是整套设计里最重要的一块，也是最容易被做错的一块。**

冲突判定依赖 `_occupied_map()`（[main.py:235–260](custom_addons/edu_schedule/controllers/main.py#L235-L260)），
它要扫 `op.session` 全表；停课日排除依赖 `edu.schedule.holiday` 的**按班匹配**规则
（[main.py:463–471](custom_addons/edu_schedule/controllers/main.py#L463-L471)）。
**这两样客户端拿不到，也不应该拿到**（别人的排课属于他人信息）。
因此：

> **右栏绝不允许出现「无冲突」这三个字。**
> 它的状态机只有两态：**「还没查」**（表单页）→ **「已查：N 条冲突 / 无冲突」**（预览页）。
>
> 如果右栏在这里画一个绿色的「✓ 无冲突」，那就是**在页面上撒谎** ——
> 用户会因为看见绿色而跳过预览页，而那一跳恰好跳过了唯一一次真检查。
> 这是本方向**最大的失败模式**，必须在评审时逐字检查。

### 2.4 「批量停用」放在哪：**顶部第二个 Tab，并就地重做**

三个候选我都推演过：

| 方案 | 判定 | 理由 |
|---|---|---|
| 右侧栏 | ❌ | 右栏是实时预览，被「停用」占掉就毁掉本方向的全部价值 |
| 同页下方折叠区 | ❌ | 只解决了「看不见」，没解决「同屏混排」；375px 下仍是 4113px 的深坑 |
| **独立页** `/timetable/deactivate` | ⚠ 最优但**要新增 GET 路由** | 与「后端契约不要改」的边界最紧张 |
| **同页 Tab**（选中） | ✅ | 同一路由、零新路由、零契约改动；基线明确允许「分页 / 分 Tab / 分步」三选一；且能带一个「有在用课时的班数」角标 |

**落地方式**：`timetable_bulk()` 已经是 `def timetable_bulk(self, **kw)`（[main.py:651–662](custom_addons/edu_schedule/controllers/main.py#L651-L662)），
读 `kw.get('tool')` 决定渲染哪个 Tab ⇒ **控制器 +2 行，纯展示分流，不碰任何提交字段名 / 提交目标**。
选 `?tool=` 查询参数而非纯前端 Tab 的三个理由：① 无 JS 可用；② 刷新/收藏/回退都停在同一个 Tab；
③ 用户能把「停用」页签直接发给同事。

**Tab 2 内部同时要重做**（否则只是把乱换个地方）：

```
┌ 停用课时 ────────────────────────────────────────┐
│ 停用 = 课时状态改成「停课」，**记录不删**，随时能改回来。 │
│ 停用后学生和教师的课表立刻不再显示它。                │
│                                                  │
│ 搜班级或代号  [ 输入班名 / 代号…            ]       │
│ ☑ 只看有在用课时的班（默认勾上）                     │
│                                                  │
│ ○ A1+A2+A3合班   在用 23 节 · 已停用 0 · 5 个科目    │  ← 单选列表
│ ○ A123+B1合班    在用 15 节 · 已停用 0 · …          │
│ ○ 人文三年级      在用 40 节 · 已停用 0 · …          │
│   （无在用课时的班默认不列出）                        │
│                                                  │
│ ── 选中「A1+A2+A3合班」后，这里就地展开 ──            │
│ 由班名推测的组成：A1（神学一年级）、A2、A3            │
│ 由班名推测，**请你确认** —— 不是系统已知事实           │
│ [ 去停用… ]  →  既有二次确认页（**一字不动**）        │
└──────────────────────────────────────────────────┘
```

得到的三件事：
1. **17 个「停用…」按钮 → 0 个**（选中后才出现 1 个）；
2. **「（推导，需人工确认）」10 处 → 1 处**，且从「每行都喊一遍」变成「你正要看它时才说一次」——警告的强度回来了；
3. **「代号」列消失**（17 处内部代号 → 0），改为搜索时的匹配关键字。

**二次确认契约原封不动**：`/timetable/batch/<id>/deactivate` 与
`…/deactivate/confirm`（[main.py:819–869](custom_addons/edu_schedule/controllers/main.py#L819-L869)）
一行不改；服务端判据「未勾选 `confirm=yes` 直接 303 回本页并带中文原因」**保留**。

### 2.5 数据可得性（右栏要什么、现在 DOM 里有没有）

这是本方案**唯一有技术风险的地方**，逐条列清：

| 右栏要用的数据 | 现在 DOM 里有吗 | 怎么拿 | 要动控制器吗 |
|---|---|---|---|
| 勾选的星期几 | ✅ 有 | 读 `input[name=weekday]:checked` | 否 |
| 开始 / 结束日期 | ✅ 有 | 读 `input[name=start_date/end_date]` | 否 |
| 重复方式 | ✅ 有 | 读 `input[name=parity]:checked` | 否 |
| 周次范围原文 | ✅ 有 | 读 `input[name=week_ranges]` | 否 |
| 勾选的班级（含顺序） | ✅ 有 | 读 `input[name=batch_ids]` 的 DOM 顺序 | 否 |
| 所选课程/科目/教师/教室的名字 | ✅ 有 | 读 `select` 的 `selectedOptions[0].text` | 否 |

### 2.6 右栏的「诚实刻度」：什么时候可以报精确节数

客户端能算的只有「星期几 × 日期范围」，**不能**算单双周与周次范围 ——
因为服务端的单双周走的是**学期周次**：`parity_ok(week_n, ctx['parity'])` 里的 `week_n`
由 `week_no_of(date, anchor)` 算出，`anchor` 来自 `_term_anchor_info()`
（[main.py:311–322](custom_addons/edu_schedule/controllers/main.py#L311-L322)）。
**若客户端按「开始日所在周 = 第 1 周」算单双周，会和服务器给出不同的数字** —— 这是真错，不是措辞问题。

所以右栏的数字分三档，措辞必须跟着档位走：

| 档 | 触发条件 | 右栏显示 | 判据 |
|---|---|---|---|
| **精确** | 每周 + 未填周次范围 + 页面无停课日 | 共 17 节 | 与服务端 `total` **必须相等**（可自动化断言） |
| **近似** | 有停课日 | 共 17 节（未扣停课日） | 服务端 ≤ 17 |
| **未知** | 单周/双周 **或** 填了周次范围 | 共 ? 节 —— 单双周和周次范围按学期算，点「预览并确认」才有准确数 | 客户端**不猜** |

选「未知」而不是「猜一个近似值」是刻意的：**一个错的数字比一个诚实的问号更伤信任**。

## 3. 交互流程

### 3.1 主流程（五步，一次提交都没多）

| 步 | 用户做什么 | 看到什么 | 校验 / 反馈在哪 |
|---|---|---|---|
| **1 进页** | 打开 `/timetable/bulk` | 左栏四组（① ② ③ 展开、④ 只露一个下拉）+ 右栏空白态「还没选课」 | 右栏第 1 段列出还差哪几项 |
| **2 填** | 每改一个控件 | 右栏第 1/2/3 段**即时**更新（**零网络请求**） | 必填项填了就从清单里消掉；日期早于/晚于的本地明显错误（结束早于开始）就地标红提示，**但不阻止提交**（服务端仍是唯一判据） |
| **3 预览** | 点右栏吸底的 **[预览并确认]** | POST `/timetable/bulk/preview`（**与现在完全同一个目标**） | 服务端 `_plan_ctx` 的 9 条校验（[main.py:358–375](custom_addons/edu_schedule/controllers/main.py#L358-L375)）逐条不变 |
| **4 核对** | 在预览页看冲突与逐日明细 | **同一套右栏语言**（见 §3.2）：要素回显 + 「已查：N 条冲突 / 无冲突」+ 周矩阵 + 逐日表 | 冲突预检结论**在这一步第一次也是唯一一次出现** |
| **5 确认** | 点 [确认生成 N 节] | POST `/timetable/bulk/create`（**同一个目标**） | 多班走 `_create_multi` 的**整批预检**：有一条冲突 ⇒ 一节都不写（[main.py:762–776](custom_addons/edu_schedule/controllers/main.py#L762-L776)） |

**步骤数没有增加**：仍然是「填 → 预览 → 确认」三步提交链，只是第 2 步从「盲填」变成「看着后果填」。

### 3.2 预览页也要说同一套话

预览页现在用的是另一套语言（「排课要素 / 周矩阵预览 / 重叠维度 / 周次锚点」）。
两栏方案要成立，**预览页必须看起来像右栏的展开版**，否则用户会觉得「右边那个和真正生成的不是一回事」：

```
预览页 = 左（同一张「你选的」回显卡，只读） + 右（检查结论 + 确认按钮）
         表头/字段名与右栏逐字一致：上什么课 / 什么时候上 / 排多久 / 给哪些班
```

- 「周矩阵预览」保留（它是红格/灰格的**唯一**可视化），但标题改成 **「按周看」**，
  逐日表标题改成 **「按日期看」**，两者并列成一个「换一种看法」的折叠区；
- 顶部固定一条**结论条**：`可以生成，共 17 节` / `有 3 条冲突，保存会被拦下`；
- **[确认生成]** 与 **[返回修改]** 一起**吸底常驻**；
- 周次表头补上日期（`第11周` → `第11周` + 小字 `09-01`），
  并修掉那个**幽灵空列**：我的实测里「周一」行第 11 周是 `none`（2026-08-31 早于开始日 09-01），
  渲染成一个孤零零的「—」，用户会以为漏排了一天（见 §8 验收项）。

### 3.3 「返回修改」必须把值带回去（对 §1.2 新增 A/B 的正面回答）

三个选项，成本递增：

| 选项 | 做法 | 成本 | 评价 |
|---|---|---|---|
| a. `history.back()` | 返回链接改成 `javascript:history.back()` | 0 行后端 | ❌ 依赖 bfcache，Odoo 门户不保证；**不可靠** |
| b. **把原参数拼进 URL** | 返回链接 `/timetable/bulk?` + 表单序列化；表单各控件 `t-att-value="kw.get(...)"` | 模板 ~15 处 + 控制器 `_render_bulk` 回传 kw（~2 行） | ✅ **推荐**。字段名与提交目标一律不变，只是「把用户已经填过的值渲染回初值」 |
| c. 会话暂存（`request.session`） | 服务端记住草稿 | 控制器 ~10 行 + 清理策略 | ❌ 多一份要维护的状态，收益不如 b |

> ⚠ **边界声明**：选项 b 是本文**唯一**建议触碰控制器的地方（除 `?tool=` 那 2 行）。
> 它**不新增/不改名字段**、**不改提交目标**、**不改任何校验**，只是渲染初值。
> 若评审认为这仍越界，砍掉后本方案照常成立 —— 只是「返回修改」继续丢值（现状）。

### 3.4 无 JS 降级

本页现在是**零 JS 的纯表单页**，两栏方案会引入第一段脚本。降级必须是硬要求：

- 右栏**服务端渲染出完整骨架与空白态**；无 JS 时它静止不动，但**读起来仍然成立**：
  「将会生成 —— 填完点下面的按钮，系统会告诉你」（而不是一片空白）；
- 核心链路（填 → 预览 → 确认）**全程无 JS 可用**，一步不缺；
- `<noscript>` 里一句：「实时预览需要浏览器脚本；直接点『预览并确认』，功能完全一样。」；
- 主按钮**永远是普通 `<button type=submit>`**，不用 JS 触发提交。

## 5. 窄屏（375px）：两栏怎么塌

**塌成「单栏 + 吸底摘要条 + 底部抽屉」，不是把两栏压扁。**

- **断点**：`≥1200px` 两栏（左 7 / 右 5）；`992–1199px` 两栏但右栏收窄（左 8 / 右 4）；
  `<992px` **单栏**，右栏整体变成吸底条。
- **吸底条**（`position: sticky; bottom: 0`，安全区内边距）：

```
┌ 375px ──────────────────────┐
│ 家 / 周期排课                │
│ 周期排课（批量生成课表）       │
│ [生成课表][停用课时]          │
│                             │
│ ▾ ① 上什么课                 │
│   课程 *   [ ▾ ]            │
│   科目 *   [ ▾ ]            │
│   …全表单…                  │
│ ▾ ④ 给哪些班                 │
│   班级 *   [ A1+A2+A3合班 ▾] │
│   ▸ 一次排多个班             │
├─────────────────────────────┤ ← 吸底
│ 每周一、周三 08:00–09:30     │
│ 17 节 · 首 09-07            │
│ [ 明细 ▾ ]   [ 预览并确认 ]  │
└─────────────────────────────┘
```

- 点 **[明细 ▾]** → **全屏底部抽屉**（Bootstrap 5 offcanvas，居中/全宽二选一），
  内容就是桌面右栏的第 2/3/4 段；关闭后可继续填。
- 窄屏**不要**把「停用课时」表原样搬过来 —— 现在这张表在 375 下会折成 **18 张卡 ≈ 4113px**
  （由 [shared_ui.xml:22–61](custom_addons/edu_brand/views/shared_ui.xml#L22-L61) 的
  `edu_narrow_table_cards` 折卡规则产生）。Tab 2 重做成「搜索 + 单选列表」后，

- 周矩阵（`ux-week-matrix` 有 `min-width: 640px`）继续走既有的 `table-responsive` 横向滚动，
  **不放进吸底抽屉**（抽屉里只放摘要与清单）。

**375px 目标**：整页 `≤ 2000px`（现状 7168px）；首屏（812px）内能看到 ① 组与吸底条。

### 推演并**否决**的四个替代形态（留档，别让下一个人再走一遍）

| 形态 | 否决理由 |
|---|---|
| **分步向导（wizard）** | 与目标正相反：向导把决策切成互不可见的几屏，用户更难看到「全部决策与后果」。且 Odoo 门户向导没有现成壳，成本更高 |
| **每次按键 fetch 一次 `/timetable/bulk/preview`** | ① 该路由返回**整页 HTML**，要 `DOMParser` 抠节点 —— 把右栏耦死在预览页的 DOM 上，改一次预览页就崩；② 每次请求都会跑 `_occupied_map()`（扫 `op.session`）；③ 违背「不加新契约」。**（P2 可考虑做成一个显式的「检查冲突」按钮，去抖 800ms，不算实时，不算 MVP）** |
| **把 occupied map 灌进页面做真·客户端冲突检测** | ① 会**把别人的排课泄露给任何能打开此页的人**（现在这个信息只经服务端聚合后以红格呈现）；② 冲突四查的判据（`_slot_conflict_dims`）要在 JS 里写第二份 —— 本仓明确禁止「不写第二套判据」（[main.py:271–273](custom_addons/edu_schedule/controllers/main.py#L271-L273)） |
| **表格/网格排课**（`docs/research/scheduling-approaches.md` §9 第 1 件） | 是**另一个更大的方向**（把表单换成格子），不属于本次「整理优化 UI」。两者不冲突：若将来真做格子，右栏「将会生成」仍可作为格子旁的后果面板复用 |

### 与外部先例的关系（铁律 0）

`docs/research/scheduling-approaches.md` §6 把「降低手工成本」的手段列成 **8 种**，
逐条核对后 **没有一种**是「表单右侧实时后果面板」：

- 最接近的是 **#2「预检查冲突（落库前先跑一遍），提示分三类」**
  （一手来源：校管家·表格排课 https://wiki.xiaogj.com/docs/biao-ge-pai-ke ）；
- 和 **#8「周期批量生成 + 模板复制」**（ClassIn「批量排课：固定规律模式」
  https://shop.classin.cn/help/appointment-course/schedule-management/ ；校管家「按循环规则批量新增」，同上）。

⇒ **本方向的增量是：把 #2 与 #8 从「提交后」提到「提交前」，并让它们常驻可见。**
**这一形态在已调研的外部系统里没有先例**（不是「查不到」，是逐条核对后确认无命中）。
按铁律 0 的要求如实标注：**无先例 ⇒ 风险自负**，安全性由「先预览后确认」这条不可动的契约兜底。

## 附：本方向的自我批评

**最大的风险不是技术，是「右栏被当成承诺」。**
用户看见右栏写「共 17 节」，很容易理解成「系统已经算过了」。而事实上冲突、停课日、
学期周次这三样它**都没算**。我用了三档刻度和一个永不说「无冲突」的诚实区来对冲，
但这依赖**落地时逐字执行**，而不是依赖用户自己看懂。

**因此我建议：如果只能保留本方案的一件事，保留「冲突与停课日：还没查」这一块。**
两块栏、四组折叠、去代号都是「整理」；只有这一块是「不让用户误以为已经检查过」——
而后者正是「先预览、确认后才写入」这条安全设计存在的全部理由。
