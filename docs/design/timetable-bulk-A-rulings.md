# 队长裁定（2026-10-04）—— 对方向 A 的两处待决

> 方向 A（`timetable-bulk-A-split-minimal.md`）交付后提出两处需裁定项。裁定如下，**并附理由**，
> 以便实现者不必再问、后来者能看出为什么这么定。

## ① 是否接受 +1 路由 +1 菜单？—— **接受**

- 新页 `GET /timetable/batch/deactivate`（约 +12 行控制器）+ `views/menu.xml` 新增「批量停用课时」菜单项（seq16）；
  排课页页脚保留一行次级链接（原型里已体现：右下「其他工具：批量停用某班的全部课时」）。
- **理由（不是偏好，是实测）**：A 淘汰了「同页 Tab」方案，因为 Tab 仍把 **17 行表 + 14 个按钮留在 DOM**；
  而在 375px 视口下那张表 **4113px = 整页 7168px 的 57%**。用户的诉求是「太乱」⇒
  「两个工具不同屏」是这次改造的**核心目标之一**（基线 §三已把它写成可判定项），Tab 达不到它。
- 用户 2026-10-03 的裁定语境也支持：他关心的粒度是「一页能不能看清」，不是「导航里多一项」。

## ② 是否加 sticky 动作条？—— **加**

- 成本：3 行 CSS + `__manifest__.py` 的 assets 段。
- **理由**：A 的投影读数是「主操作 1220px → 738px（进首屏）」；但**三个折叠全展开时回到 ~930px**，
  比 900px 的首屏线**差 30px** ⇒ 不加就等于「在最复杂的那种用法下，主操作又掉出首屏」。
  而基线 §三把「主操作在首屏」写成了目标 ⇒ 不加以防万一，目标在边界情形下不成立。
- 30px 的差距用 sticky 兜住，比让用户滚动更划算。

## ③ 顺带确认的三件事（A 已做，无需再议）

1. **零新增 CSS/JS**：`details/summary` + Bootstrap 5 `.btn-check` chip，A 已**实测**勾选后的底色与焦点环；
2. **契约一行不动**：模型层与提交目标不变，控制器只做加法（6 处）；
3. **投影读数不是已落地读数** —— A 自己在交付里写明了这一点。**改完必须用基线 §4 那把尺子复测**，
   并把「改前 / 改后」两列一起写进交付报告（只报改后等于没有对照）。

## ④ 与缺陷修复的顺序（避免撞车）

`backend-ux` 正在修的三条（校验失败清空表单 / 预览页「返回修改」回空白 / 「整周复制」等过时文案）
**先落地**；视觉重设计随后 **rebase 在它之上**。原因：三条缺陷改的是**同一批模板与控制器**，
并行改必然互相覆盖（本会话已经因为「同一张卡派给两个人」出过两次撞车）。
