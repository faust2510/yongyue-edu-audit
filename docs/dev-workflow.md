## 第 0 步：落地前查重（**先走这一步，再进六步闸门**；2026-09-17 立）

> 依据：`docs/audit/feature-overlap-audit.md`（8 类重叠的四层证据）——本轮收口证明，
> 「多波次并行开发」会长出一个功能的两套实现（打卡 ×2、评估 ×2、岗位 ×2、op.student 双根菜单 ×2）；
> 每一次都要靠**事后**合并、迁移、加兼容层来还债，代价远高于**动手前**查一次。
> 本步的产出不是文档，是一个**结论**：新东西该不该新建、建在哪里、谁拍的板。

**给谁看**：任何「新增模型 / 新增门户路由 / 新增后台菜单 / 新增模块」的需求——包括 AI 助手与子代理，
开工前逐条勾（不允许"我记得没有"）：

- [ ] **① 查 code-map**：`docs/code-map.md` §4「自研模块地图」逐模块看一遍模型归属与入口现状；再看
      §5「路由速查」——**本仓现成的功能清单只有这一份，先信它，再信记忆**。
- [ ] **② 查同义模型/入口**（每条都要留"扫过哪里"的证据：命令 + 命中行号；**没找到也要留**）：
      ```bash
      # 按模型名/前缀全仓搜（不要只搜一个模块目录——跨模块的功能按名字全仓搜）
      grep -rn "edu\.<候选前缀>\|class Edu<候选名>" --include="*.py" custom_addons/
      # 按门户路由全仓搜（同一功能的两个名字往往连写法都不一样）
      grep -rn "<候选路由>\|/my/<候选>" --include="*.py" custom_addons/
      # 按后台菜单名/动作模型搜
      grep -rn "res_model=\"<候选模型>\"\|<候选菜单名>" --include="*.xml" custom_addons/
      # 菜单与数据实况（只读）
      docker compose exec -T db psql -U odoo -d edu19 -c "select id, active, name->>'zh_CN' from ir_ui_menu where parent_id is null order by id;"
      ```
      ⚠ 「我扫了 X 目录/用 Y 方式没找到」——**搜索范围本身就是结论的一部分**：报「不存在」必须写明扫了哪些范围、
      用什么方式（**grep 命中行号 ≠ 活路径**；路由要连同控制器与模板一起看）。
- [ ] **③ 写进设计摘要**：`docs/plans/<功能>-design.md` 加一节「既有实现对照」，逐条写：
      查了什么 / 命中什么 / 为什么不复用。**没有这一节的 design 不进入第 4 步**。
- [ ] **④ 查「升级会不会动业务数据」**（2026-09-17 追加，依据 `docs/audit/finding-F5-edulife-demo-injection.md`）：
      看一眼 manifest 的 `data` 列表里有没有**对业务模型执行写操作**的 `<function>` / 种子函数——
      `data` 每次 `-u` 都重放，`demo` 才只在安装且开启演示数据（`--without-demo` 之外）时装载。
      ```bash
      # 本模块声明了哪些 data / demo（data = 每次升级重放）
      grep -nE "'data'|'demo'|\"data\"|\"demo\"" custom_addons/<模块>/__manifest__.py
      # data 文件里有没有"写记录"的函数调用
      grep -rn "<function\|_load_demo\|create(" custom_addons/<模块>/data/ 2>/dev/null
      ```
      · 演示数据必须走 `demo` 键、且**带【演示】标记**；写业务表的种子函数**不得**放在 `data/`。
      · 反面实例（真实踩过）：`edu_life/data/demo_life.xml` 末尾的
        `<function model="edu.checkin.type" name="_load_demo_records"/>` 按"今天"取滚动 7 天，
        每次 `-u edu_life` 都可能把**无标记的演示行写进业务表** `edu.checkin.record`（本轮实测净增 9 条）。
        它是「同日幂等、跨日补写」——**只测一次同日会得到"幂等"的假绿**。
- [ ] **⑤ 设计摘要写明演示数据策略**：新功能的演示/样例数据放哪、怎么标记、怎么清理（一句话即可）。

### 查到重复怎么办（三步，缺一不可）

0. **先停手**：命中上面 ④（无标记演示数据 / 升级写业务表）的，**不是"登记后继续"**——整改完再回到六步闸门
   （演示数据挪到 `demo/` 或加环境闸门；确需保留就给写入行加【演示】标记）。
1. **不得直接新建**（不允许"先建着，之后再合"——本轮的每一处重复都是这么长出来的）。
2. **登记**：在 `docs/audit/deprecated-inventory.md` **追加一行**，写清「重叠对象 / 证据（模型 / 菜单 id /
   路由 / 数据条数）/ 候选方案」。台账是**追加**的，不许覆盖历史行。
3. **请队长裁定**——业务口径类（涉及用户可见变化、数据归属、命名）由队长提交校长拍板。
   裁定只有三种结果，**必须落成台账里的一个字**：
   | 裁定 | 含义 | 台账里怎么写 |
   |---|---|---|
   | **复用** | 用既有实现承载，扩展它 | 「替代路径 = <既有模型/路由>」+ 扩展方式 |
   | **合并** | 新旧两套都留记录，只留一个入口/一份引擎 | 「保留原因 / 替代路径 / 何时可彻底删除 / 删除前置条件」四栏**全填** |
   | **新建（并存）** | 确无先例、或业务上必须两套 | 必须写「为什么不复用」+「重新考虑/收口的触发条件」 |

### 谁裁定

| 事项 | 裁定人 |
|---|---|
| 是否重复、该复用/合并/新建 | **队长**（本仓唯一裁定入口） |
| 涉及用户可见变化、命名、数据归属、是否计入某统计口径 | 队长 → **校长**拍板（本轮 3 项待拍板即此类） |
| 台账登不登记、字段缺没缺 | 队长 / 复核人（t8 一类最终闸门） |

### 脚本化条件（本轮不实现，先定判据）

- 判据：**同一功能第三次出现重复**（同类模型或同类入口第三次落地）⇒ **必须**脚本化，不再靠人工 grep。
- CLI 草案：`python3 scripts/check_feature_overlap.py --module <edu_x>`——输出该模块声明的每个模型中
  「已有同类模型 / 已有同类门户路由 / 已有同类后台菜单」的清单，退出码非 0 表示**命中重复**。
- 体例照抄现有静态门禁：`scripts/check_manifest_tracking.py`（零环境依赖）、`scripts/check_view_xpath.py`
  （`--selftest`）。**必须带 `--selftest` 与一条"应当报红"的探针**——先把探针单独喂给判据看它报红，
  再放进链路里（参见本文「造『应当报红』的探针之前，必须先证探针本身命中」）。

> **一句话**：第 0 步不是"看一眼"，是**留一份能被人复核的查重记录**；查重记录缺失 = 第 4 步不许开工。

## 已知陷阱：**跑验证之前**先确认这两件事（2026-09-17 立，两条都是实测踩出来的）

> 不是"注意事项清单"，是**判据的前置条件**——不满足它们，你测出来的数字本身就不代表你以为的东西。

### 陷阱 1：`-u edu_life` 会往业务表补演示打卡 ⇒ **任何计数型验证/对账前，先确认最近有没有跑过它**

- **机制（读源码 + 实测）**：`edu_life/data/demo_life.xml` 末尾有
  `<function model="edu.checkin.type" name="_load_demo_records"/>`，而该文件在 manifest 的 **`data`**
  列表里 ⇒ **每次 `-u edu_life` 都执行**。函数按**滚动窗口**补演示打卡
  （读经近 7 天 / 灵修到昨天；今天留给门户「一键打卡」演示），目标是**业务表** `edu.checkin.record`，
  另外还会补一篇 `edu.journal.entry` 演示周记。
- **后果**：**每跨一个日历日再跑 `-u edu_life`，就可能再补一批**（同一天重复跑则被 `search_count` 挡住）。
  实测：t2 跑一次 `-u edu_life` 之后 `edu_checkin_record` 多出 **9 条**（ids 53–61，
  `create_uid=1 __system__`、`create_date` 同一秒），而当时全队正在做打卡迁移对账 ⇒ 计数莫名漂移、
  对账人对不上账（见 `docs/audit/finding-F3` 与 `finding-F5`）。
- **规矩**：凡做**计数型**判定（对账表、零增长断言、迁移前后对照、报表数字），**先执行**：
  ```bash
  # ① 看最近的升级窗口（本地：/tmp/edu19_upgrade.*.log 的时间戳与模块名）
  ls -lt /tmp/edu19_upgrade.*.log | head -3
  grep -l "edu_life" /tmp/edu19_upgrade.*.log | tail -3
  # ② 看"最近写入"（用状态表，不用统计表）
  docker compose exec -T db psql -U odoo -d edu19 -c \
    "select count(*), max(create_date), max(write_date) from edu_checkin_record;"
  ```
  若最近跑过 `-u edu_life`，就把这批增量**单列出来**（来源/时刻/id 区间），不要让它们混进"迁移/功能"的账。
- **同类观察**：注释里写的"重复执行 `-u` 保持幂等"只覆盖**同一日历日**；"相对今天滚动"这一维没写进注释——
  **只测一次同日会得到"幂等"的假绿**（同族：`docs/dev-workflow.md` 判据强度第 5 条）。
- **状态**：**t12 正在修成幂等**（根因与建议见 `docs/audit/finding-F5-edulife-demo-injection.md`；
  台账 `docs/audit/deprecated-inventory.md` §6 的 F5 行）。修完之前，这条前置条件一直有效。

### 陷阱 2：改了路由实现 ⇒ 必须有**一条"打完就摸页面"的判据**

- **事实 1**：`bash scripts/safe_upgrade.sh <模块>` **EXIT=0 只能证明"装载没炸"**，不证明"路由能跑"。
  本轮 `/my/checkin/board` 的 `NameError: name 'datetime' is not defined` 就是这样漏过去的——
  升级 EXIT=0、无 Traceback，页面却 500（见 `docs/audit/finding-F2-checkin-board-500.md`）。
- **事实 2**：抓回它的**不是评审，也不是升级日志**，而是 t5 自己写的页面级断言
  `python3 scripts/migrations/verify_checkin_board.py`（"教师访问 = 200 **且**看板勾数 == 库内本周到堂数"）。
  ⇒ 规矩：**改了路由/控制器（尤其换了数据源），验收里必须有一条真的去 GET 那个页面、并核对页面上的数字**；
  只跑升级 + 只静态读代码都不算。
- **配套（同一族的假绿）**：判"页面 200"时，**探测函数不许跟随重定向**。
  `tests/smoke/ux_v3_route_matrix.py:229` 的 `probe()` 用的是 `allow_redirects=True`（跟随），
  于是"旧路由改成 303 → 新页 200"会被**判成 PASS**——把收口的成果变成盲区。
  正确写法（同一文件 `:187` 已有先例）：
  ```python
  r = sess.get(BASE + path, timeout=15, allow_redirects=False)
  assert r.status_code == 303 and r.headers.get('Location') == '/my/checkins'
  ```
  ⇒ 断言要写成 **`first == 303` + `Location` 精确匹配**，不要用"跟随后 200"。
- **连带**：这条与「第 0 步闸门」互补——闸门防"多长出一个重复"，本条防"改完了没人摸过"。
  凡本轮改过 303 的旧路由，断言清单见 `docs/audit/checkin-merge-report.md` §10.2。

## 实现约定（从本项目既有代码提炼）

- 模型字段命名用 Odoo19 新法：`group_ids`、`<list>`（无 tree）、`invisible="expr"` 新语法
- 权限：不建自定义组，复用 `base.group_portal / group_user / group_system`，ACL 写各模块 `security/ir.model.access.csv`
- 角色分流：控制器里 `current_student()/current_faculty()/current_parent()` 判空分流，不做组判断
- 门户页面：模板外壳 `t-call="edu_portal.edu_page"`；写操作走兄弟路由 `/xxx/save` + csrf
- 后台菜单：根菜单 `<menuitem name sequence groups>`，动作 `act_window` 中文命名
- 种子脚本放 `scripts/seed_*.py`，必须幂等；演示内容须标注【演示】
- Git 提交：暂存区有无关文件时用路径限定提交；注意 `git commit -- <file>` 对 untracked 文件无效，须先 `git add <file>` 再 `git commit -- <file>`
- 本地升级一律用 `bash scripts/safe_upgrade.sh <模块>`（串行锁 + DB 参数 + `--no-http` + 默认 `-i` + 挂载新鲜度自检 + 失败特征硬失败）；**退出码 0 不等于升级成功**，务必看输出里有无 `manifest not found` / `Traceback` / `CRITICAL`
- **改了模块 .py 就必须重启 web 进程**（注册表重载 ≠ 重启）：`-u` 升级只更新数据库与**执行升级的那个进程**，
  跑着的 web 进程仍用旧注册表（**新文件不会被 import**）⇒ 模型「库里有、活体进程没有」（生产先例：班级管理/课代表/专业·学制三个功能暗 5.7 / 2.9 / 2.0 天）。
  本地改完 .py：`bash scripts/safe_upgrade.sh <模块>` **之后**执行 `docker compose restart web`；
  远端由 `scripts/deploy_myedu.sh` 负责（已内置重启 + 有界就绪探活）。判据 = `python3 scripts/check_live_registry.py`
  （有 DARK ⇒ exit 1）。机制、三种症状与事故日期见 `docs/code-map.md` §10.1。
- **公开页文案闸门只管「事实」，不管「术语」**（2026-09-12 v3 定案）：数字/日期/费用金额/联系方式/资质才需要用户确认；**术语统一（如「学费→统筹费」）按用户既有指令直接执行**，不要把闸门扩大到措辞层——否则会让整条流水线为一个已明确指示过的问题空等一轮
- **QWeb 继承视图三件套**（2026-09-12 t7 三轮踩坑，全部现场实证）：
  1. **改 xpath 前先对父视图验证表达式命中数**（lxml 逐条跑，如 `//table//tr/td[1]` = 1）——继承失败只在装载/渲染期暴露，"改完再试"要来回好几轮；注意行被 `<t t-foreach>` 包裹时 `tbody > tr` 不成立，要用 `//table//tr`。
  2. **在 `t-else` 元素前插入兄弟节点会打断 `t-if`/`t-else` 相邻性** → 装载期 `SyntaxError`；要锚到更外层。
  3. **内联 `<script>` 里的裸 `<`（如 `for (i = 0; i < n; i++)`）必须转义为 `&lt;`** —— lxml 是严格 XML，本轮它让 `-u edu_portal` EXIT=255，**阻塞了全队升级**；改完建议自检 `python3 -c "import xml.etree.ElementTree as ET; ET.parse('<文件>')"`。
- **互补 ≠ 并集完备：扫描工具的覆盖率必须是"可审计的声明"**（2026-09-12 t26/t37 教训）：两个门禁分别覆盖不同属性，看起来"合起来很全"，但**只要有一条可见文案走它们都没列到的属性（`aria-description`、`data-tooltip`…），两边会同时漏**。
  · 要求：每个扫描工具的 docstring **明写"本工具覆盖哪些位置"**（文本节点？哪些属性？哪些文件类型？），并在输出里声明未覆盖项；
  · 反面教训：本轮 "0 命中" 是抽样口径下的假绿（`check_odoo_trace` 不扫属性 × `check_english` 遇 CJK 即跳过），两个盲区恰好互补。
- **无法被一次"行为级测试"证实或证伪的 claim，应降级为"设计意图"，不要写成断言**（2026-09-12 study-eng 提出）：
  · 例：t7 写"改分唯一入口、全部留痕"是断言 → 于是必须配"写一次看留痕表"的行为验证；若当时只写"设计上应当留痕"，就不会有"claim 不成立"的 finding，也就没人会去修。
  · 行为级验证的三段模板：**① 绕过被测路径**（用模型边界写，而不是走门户，否则只测了门户）→ **② 读真正的产物**（查留痕表，而不是看返回值）→ **③ 还原并断言 `leftover=0`**（同一份数据上"缺陷存在"与"缺陷已修"都可复现且互不污染）。
- **凡"全绿/已归零"的结论，必须附「覆盖对象 + 未覆盖项」**（2026-09-12 t26/t37 落地）：
  · 例：`check_view_xpath` 输出"跳过 22 处跨模块继承"；`check_english --coverage` 打印覆盖与不覆盖的位置清单；
  · 把覆盖率从**隐含假设**变成**可审计的声明**——否则读者会把"我扫过的都绿了"误读成"系统是干净的"。
- **任务模板：新增模型 / 新增 `_inherit` 的改动，verify 默认带上 `python3 scripts/check_view_xpath.py`**（2026-09-12 flow-eng 复盘）：
  · 那起注册表 P0（`_inherit` 目标在更晚导入的文件里）**静态检查器能精确报出**（`IMPORT-ORDER … 把 registration 提到 exam_session_ext 之前`，exit 1）；
  · 缺的不是工具，是**当时的 verify 没包含它** —— 所以写契约时，凡涉及新增模型或新增 `_inherit`，verify 里默认加这一条（`safe_upgrade.sh` 已在取锁前接入，属第二道）。
- **「模板源干净 ≠ 已落库的记录干净」**（2026-09-12 brand-eng/flow-eng，邮件面）：模板**源文件**（或你新建的覆盖）干净，不代表**数据库里已有的记录**干净 ——
  `mail.template` 的 `subject/body_html` 是**数据列**（经 `mail.render.mixin._render_template` 渲染，不是 `ir.qweb` 具名模板，`t-inherit` 与 `_render` 都够不到），
  所以必须**用真实渲染路径**（`tpl._render_field(field, [uid])`，**逐语言**）证明库内记录也清了。
  · 这条对 `noupdate=t` 的记录尤其关键：普通 `<record>` 与 PO 都改不动它们，只能 `<function>` 每次 `-u` 重放。
- **同一个汇总行不能有两套口径**（2026-09-12 brand-eng 自查）：它同时打印「覆盖 4/8 支模板」与「8 支模板全部覆盖」—— 因为 4 条 `mail.template` 目标走了另一通道、没被计入「覆盖」分子。**同一行两种说法 = 口径分支 = 假绿家族的又一形态。**
  · 修法：**两处共用一个口径函数**，改无歧义四段式（候选 N / 渲染成功 N / 未覆盖 N / 数据记录待修 N）。
- **「不稳定的红」与「错误的绿」是同一种病的两面 —— 都由无效判据引起**（2026-09-12 study-eng，t56）：
  · **不稳定的红更隐蔽**：它看起来像"产品有问题"，其实是判据在骗人（例：用**数字子串**当泄漏判据 —— `str(att_id) in r.text` 在 38KB 页面里几乎必然偶合；同一 URL、同一 200、同一长度，第 1 轮 True 第 2 轮 False）；
  · **弱信号只能"记录"，不能"判定"**：判定用强信号（完整名称/唯一串），弱信号（数字、短串）单列进证据便于人工看；
  · **比较键要选有意义的终态**（例：别比"清场后读不到的 marks"，那会得到 GONE vs None 的随机红；改比 `leftover_exam`/`history_leftover`）；
  · 推论：**「稳定通过」本身不是证据** —— 载体不合法时测试反而会稳定地绿（t43 上次：越权方没有教师身份 → 每次都 303 → 看起来完美）。**先断言载体合法，再看通过与否。**
### 判据强度五兄弟（同一句话的五种形态）

> **别让「通过了」由更弱的现象支撑。**

| # | 形态 | 典型翻车 |
|---|---|---|
| 1 | **claim 与证据要同级** | 写"唯一入口、全部留痕"，却只读了代码没查留痕表 |
| 2 | **某个门禁没报 ≠ 那一处干净** | 门禁不扫属性 / 遇 CJK 跳过 → 两个盲区互补，报绿 |
| 3 | **验收写结果，不写手段** | 契约写 xpath，而目标是"库内记录干净" → 假阻塞（t52→t54 A/B） |
| 4 | **测试载体必须先被断言合法** | 越权方没有教师身份 → 6 条断言每次都 303，**稳定地绿** |
| 5 | **量具本身不许有副作用** | 读一次状态却改了环境（跑 `CREATE EXTENSION` / 查统计表）⇒ 判据随时钟漂移、读数过期（t6 2026-09-17 实例） |

- **「量具自己动手改了环境」+「量具把现状当目标」——判据的两种新病**（2026-09-17 docs-eng，t6 实测）：
  · 实例一（我做错的）：给台账取"何时可彻底删除"的证据，要求「连续 N 天无写入」⇒ 我去查 `pg_stat_user_tables.n_tup_ins`。
    但该计数**不是**"最近一次改动"（`stats_reset` 前都是**累计值**），拿它当"最近写入"会得到随时钟漂移、
    与环境年龄绑定的结论；更糟的是我为它跑了 `CREATE EXTENSION pg_stat_statements`——**一次"只读核对"动了库全局状态**。
    正确做法：**用状态表**（`select max(create_date) from <表>`）而不是统计表；统计表只做旁证，必须带采集时刻 +
    快照，且**永远不要为了读数去改环境**（改了要在结论里当场认账）。
  · 实例二（t2 的，机制同族）：菜单生成器**把"库内现值"当成"目标值"写回 XML** ⇒ 所有要停用的改动**静默丢失**，
    而对账器却一致（因为两边读的是同一个污染源）。⇒ **"目标值"只能来自计划声明源，不能来自被测对象本身。**
  · 一句话：**判据与量具必须与"被测对象"和"时间"都解耦**——读一次状态就改一次环境，或把现状当目标，
    都会让文档与断言一起过期，而且看不出错。
- **写「判据/台账」类文档时，文中命令必须逐条实跑再提交**（2026-09-12 i18n-eng，t59）：它在提交前跑了一遍自己写的命令，**当场抓到两处"写完几分钟就过期"的内容**（一条样本已被后续修复翻篇、三处引用的门禁数字已从 11 变成 10）→ 否则文档一发布就是旧数。
  · 配套：台账**不带任务状态**（grep completed/pending 等 = 0），只写「判据 / 证据（命令+数字+日期）/ 如何复核」。
- **汉化类事故的三种形态（都不是"翻错了"）**（2026-09-12 i18n-eng 收束）：
  · **「以为覆盖了其实没覆盖」**（PO 灌了但 `noupdate` 不生效，且**静默留在库里**）；
  · **「以为查过了其实只查了退化子集」**（探针上下文缺字段/缺身份 → 只渲染了 10% 的内容）；
  · **「以为清了其实只是没算进去」**（不计入判据的面被当成已清）。
  · 核心永远是同一句：**口径说清楚、量具先自检、证据落到命令。**
- **「断言自身有缺陷」家族（与假绿并列）**（2026-09-12 verifier 归档）：

  | 实例 | 缺陷形态 | 后果 |
  |---|---|---|
  | 取值字段名错 | 载荷是 `id/badge/text/cta/url`，却按 `title/name` 取值 | **假绿** |
  | 空 recordset 真值 | `bool(env["edu.grade.history"])` 天然为假 | **假红** |
  | 载体未先证合法 | 夹具没生效就当证据 | 假绿/假红 |
  | 查询串回显算命中 | 页面回显 ≠ 搜到 | **假红** |

  · **共性判据：断言必须先自证忠实**（字段名对、空态≠缺陷、夹具确实生效、判据能被反例证伪），**再拿它去量被测对象**——否则测出来的是断言自己的毛病。
  · **造"应当报红"的探针之前，必须先证探针本身命中**（2026-09-13 flow-eng 自曝，t109）：它用 `printf \u0024…` 写入 `$`，而 **macOS 的 `printf` 不认 `\u` 转义** ⇒ 探针里**没有真 `$`** ⇒ 检查器不报红 ⇒ **gate 放行 → 脚本真的升级了一次（且未先报备窗口）**；
    **正确顺序**：**先把探针单独喂给目标判据、看它报红**，**再**放进"应当被拦住"的链路里；否则你验的是"链路放行了"，却以为验的是"链路拦住了"。
- **「在某目录里没找到」≠「不存在」**（2026-09-12 flow-eng 自我更正，t27）：它只在 `edu_portal/` 内 grep 路由，误判 `/quiz` 是死链；实际定义在 `custom_addons/edu_quiz/controllers/portal.py:16`。
  · 与「没测到 ≠ 不存在」同族，只是对象换成了**代码/路由/引用**：**搜索范围本身就是结论的一部分** —— 报"不存在"必须写明**扫了哪些范围、用什么方式**；
  · 实践：`grep` 加 `--include` 限定扩展名是对的，但**不要限定单个模块目录**；跨模块的功能（如 `/quiz`）要按路由名全仓搜索。
- **判定「漏项 vs 有意设计」用对照，不用单点**（2026-09-12 flow-eng，t27 的范例）：
  · **同页对照**：同一函数的「校历活动」分组**做了**班级收敛，而「测验/网课」分组没有 → 说明本页**有**收敛设计，只是没施加到这两组；
  · **跨页对照**：`/my/courses`（`lms.py:45`）走 `_subjects_for(...)` 得到本角色科目 → 课程页是收敛的；
  · 两条对照合起来才能下"这是漏项、不是有意全库目录"的结论；**单看一处只能猜意图**。
- **「不做的项」也要显式处置**（2026-09-12 study-eng 提出，队长采纳）：每一条被识别出的缺口，都要落到三种处置之一 —— **归某个任务 / 另立任务 / 明确不做并写明理由**；**不能悄悄消失**。
  · 实例：t67 的 ③「在修复前版本上真打一次该路由、观察 500」→ **明确不做**：唯一收益是把「修复前会崩」从推断升格为观测，**不改变修复是否正确**，而成本是一次**共享状态窗口**（切版本 + ≥2 次 `-u`）；
  · **一句话**：**保留一条标注清楚的推断，比为了好看去补一次窗口更符合纪律** —— 因为我们的规矩本来就是「不把推断升格成观察」，而不是「把所有推断都变成观察」；
  · 与「不计入判据的面不得当成已清」同构：**"不做的面"也不得当成"已做"**；
  · **防塌陷（2026-09-12 study-eng）**：三种处置里「明确不做」成本最低 → 规则会自然向它漂移（**最难填的是「无」，最便宜的是「不做」**）⇒ **「明确不做」必须带一个「重新考虑的触发条件」**（可观察、可判定的事件，如「若该缺陷再现一次」「若将来有任务本来就要开窗口」「若库中出现合法样本」）；
    - 差别很实在：**带触发条件的「不做」是可复活的**（条件一出现就有人认得出来），**不带条件的「不做」是终态的**，与「忘掉」在文档上不可区分；
    - 三种处置的形式：归某任务 → 写明任务号；另立任务 → 写明依赖；**明确不做 → 写明唤醒条件**。
    - 一句话版：**「不做」也要有唤醒条件，否则它不是决定，是遗忘。**
  · **唤醒条件分三种强度，可靠性差很多**（2026-09-12 study-eng）：

    | 类型 | 形态 | 可靠性 |
    |---|---|---|
    | **机会型** | 「日后若有任务本来就要开 X 窗口 → 顺路带上」 | **最优先**（零额外成本、必被经过） |
    | **里程碑型** | 「探活矩阵建成即关闭」 | **可判定、可靠**（依赖另一件事完成） |
    | **事件型** | 「若出现此类缺陷即升级为…」 | **要等它真的发生** |

    - **事件型的性质要说白**：对**代价可控**的项它合理（出事再处理）；对**后果不可逆 / 代价高**的项，**事件型实际上就是「不做」** —— 它把「第一次发生」当触发器，而**那一次已经进了生产**；
    - **升级办法**：给事件型至少配一个**成本极低的探测动作**，把它变成机会型/里程碑型（例：在门禁的「已知不覆盖」声明里**点名**该类构造，或**下次动该门禁时顺手加一条样本**）；
    - 一句话版：**唤醒条件优先选「零成本顺路」或「可判定里程碑」；「等它发生」只配用在赔得起的事情上。**
- **「替换一半」：改一个定义时，必须连同它的消费者一起改**（2026-09-12 flow-eng 自曝的机制）：
  · 实例：t67 的替换**只改了上半段**（`regs.browse + filtered` → `scoped_records`），**没同步处理下半段的消费者**（`skipped = len(regs) - len(pending)` 仍引用 `regs`）→ 定义被删、消费者残留 → 每次被允许的调用都 `NameError`；
  · **可执行的动作（成本几秒）**：改完之后 **grep 那个被删掉/改名的标识符**；**但要限定作用域**（2026-09-12 flow-eng 补）—— 消费者可能不在被改文件里，且**同一名字在别处合法存在**（它的活例：`regs` 在 `enroll.py:345` 是合法局部变量，全文件 grep 会命中，但那命中**不是**"替换一半"）；
    **判据**：**逐个命中判断「该处所在作用域里这个标识符是否仍有定义」** —— 只有落在「你刚删掉定义的同一作用域」内的命中才判失败。这样既不漏（能抓同一方法内的悬空引用），也不误报（不因同名局部变量造假红）；
  · 与「必须实际调用一次」是**预防 + 兜底**：前者靠**搜索**（改完立刻、零成本、可离线），后者靠**执行**；两者都拦不住的是**动态构造的标识符/属性访问** —— 那只能靠真实调用。
  · 这类"删了定义但留着引用"**语法上是合法的**（Python 到运行期才报错），所以静态检查与 `import` 都拦不住 —— 只能靠**搜索引用**或**实际调用路径**。
- **写路由（POST）是本轮门禁体系里最弱的一面：常态是「装载过、从未执行过」**（2026-09-12 study-eng + flow-eng）：
  · 原因：路由矩阵跑 GET；POST 需要 csrf + 载荷且可能改数据 → 不做例行探活 → **`-u` 与 `import` 只能证明装载**；t67 那条 `NameError` 正住在这类里；
  · 治法：**给每条写路由登记一个「安全目标」**（越权 id / 不存在 id / 空载荷 / 非法 state），跑一发**非变更探活**，期望 **3xx 而非 500**；三条收紧：① **先断言安全目标确实越界/不存在**（否则 3xx 可能只是对合法载荷的正常拒绝 = 测了个寂寞）；② 除 3xx 外**断言相关行未被改动**（读回原值）——「能走完」与「没动数据」是两件事；③ 顺带断言 `ok/fail/skip` 计数语义（如越权 `skip=0`）。
- **边界往往是「劈开的」—— 所以边界要写进测试，不能只写进文档**（2026-09-12 brand-eng，t78 实测）：
  · 它给「动态构造标识符」这条不覆盖声明做可选样本时，实测发现这类边界**不是一刀切**：`data-tooltip="…Odoo…"` **不扫**（不在 `ATTR_RE` 清单）；而 **`data-title="…Odoo…"` 会被扫到** —— 因为 `data-title` 含子串 `title=`，命中了 `ATTR_RE` 的 title 分支；
  · **只写文档**会让人以为"`data-*` 一律不扫"；**写进测试**才把这个"**部分覆盖**"的事实固定下来；
  · 规矩：宣布一条不覆盖时，**顺手做两条样本**（一条确实不覆盖、一条其实覆盖），并写明现状 —— **"意外收获"也是收获，值得写下来**。
- **把新样本纳入 selftest 时，必须同时声明「期望规则名」**（2026-09-12 t74 的机制在 t78 当场生效）：
  · 现象：加完第二条样本后 selftest **立刻红** —— `期望规则名不符：… 期望 [] 实际 [attr-odoo-value]`，正是 t74 刚加的「红了**且**红的正是预期那条」在拦；补上 `EXPECT_RULES` 后全绿；
  · 意义：**机制刚建好就在下一次改动里自我执行了一次** —— 这是它有效的现场证据，也说明"把要求变成断言"确实能接管人的记性。
- **「没触达路径」有三种形态**（2026-09-12 flow-eng 的归类，把分散的几条收在一个名下）：

  | 形态 | 表现 | 防线 |
  |---|---|---|
  | **装载 ≠ 执行** | `import` / `-u` 无 Traceback，但方法体从未运行（t67 的 NameError 就住在这里） | 实际调用一次该入口 |
  | **探针走了另一条路** | 探针自建调用，未与实现**逐字同形**（例：实现是 `p2.sudo().write(...)`，探针走了别的写法） | 探针**与实现逐字同形**，并断言"效果发生"了 |
  | **被授权门短路** | 只测"越权"分支，受保护代码从未执行 | **正对照**（唯一能走到受保护代码的路径） |

  · 共同点：**代码"看起来跑过"，但目标那段没被执行** —— 与「检查走错了面」同族，一个在**被测代码**侧，一个在**检查工具**侧。
- **「载得进」不能推「跑得通」：改了方法体，验证必须实际调用一次该路径**（2026-09-12 flow-eng 自曝）：
  · 实例：它在 t67 的替换里删掉了 `regs = ...browse(...)` 定义行，而下方仍引用 → **该路由每次被允许的调用都 NameError**；它的验证只看"**升级日志 0 Traceback + import OK**"，而 **import 不执行方法体**，该路由又从未被调用；
  · 与本轮"量了但不覆盖"同族，但更隐蔽：**量对了对象、却没触达路径**；
  · 规矩：**任何改动落在"方法体/路由体"上时，验证必须真实调用一次该入口**（哪怕只调用一次得到业务错误，也比"载得进"强）。
- **改"路由清单/规则族清单"这类声明时，声明与事实要对拍（漂移即 FAIL）**（2026-09-12 brand-eng 提案）：静态清单是**声明**，代码里的实际字面量是**事实**；新增一条却忘了同步清单 → 机制**静默漏掉**它。
- **当风险是"读者会扫读跳过标签"时，用结构（分栏/分组）而不是字段**（2026-09-12 study-eng，t83）：

  · 构造器可以内部 fail-fast 断言（例：建完教师就断言 `current_faculty()` 能解析），**但断言结果必须回传/打印出来**；

- **活文档的真正维护成本在「结构」，不在「事实」**（2026-09-12 i18n-eng 的判断，队长采纳）：

- **「活文档」与「历史记录」两类交付物的维护规则不同**（2026-09-12 i18n-eng 提出，队长裁定）：

  |---|---|---|---|
  | **活文档（事实型）** | 判据台账、门禁规范、code-map、流程文档 | **可以且应当** | ① 更新前**实跑复核**（否则改完仍可能是旧数）；② 报告 diff + 理由；③ 权威值在工具里，文档只引用 |

  · 依据（i18n-eng 的论证）：台账的**全部价值就是"现在是对的"** —— 一份写着旧数字的判据索引**比没有更糟**：后人照旧数复核 → 得出"文档与现实不符" → 从此不信这份文档；

- **登记表不是"看着没用就塞进去"的垃圾桶**（2026-09-12 i18n-eng）：`UNREACHABLE_MODULES` 这类登记表，**每条都要能回答"为什么不可达"**；并且**必须有反例**（例：`calendar` 4 条会议模板经判定**可达**故留在待修）—— 只有正面清单、没有反例，后人会把它当垃圾桶用。
- **对「正在通过的测试」做重构，必须锁定断言数**（2026-09-12 study-eng）：重构后仍须**断言数不变 / 全 PASS / 两轮一致 / leftover=0**；

- **「常量忘了同步」是判据元数据错 —— 它让门禁红得没有信息量**（2026-09-12 i18n-eng）：
  · 例：`check_odoo_trace` 有 `EXPECTED_ASSERTIONS = 24` 与运行时实际值比对（漂移即 FAIL）；**为实现时间戳而新增断言时若忘了同步该常量，门禁会把自己判 FAIL** —— 红的原因是"忘了 +1"，不是真有问题；
  · 危害链条：**红得没有信息量 → 被当成噪音忽略 → 久而久之没人看退出码 → 一个被忽略的门禁比没有门禁更糟**（它还占着"已验证"的信誉）；
  · 对策：① 能不加断言就不加（**优先只打印**）；② 必须加时**同一提交内同步常量**；③ 汇总行把"断言数漂移"单独表述，让人一眼看出这是元数据问题而非命中问题。
- **自证机制本身也要有断言**（2026-09-12 verifier，t60）：除了断言数漂移自检，还要断言"指纹是 8 位十六进制" —— 防止**指纹函数被改坏却仍打印一行像样的自证**。
- **「独立复核」有三层，越往下越硬**（2026-09-12 study-eng，t56/t61 之间）：

  | 层 | 做法 | 能发现什么 | 发现不了什么 |
  |---|---|---|---|
  | **环境层** | 换人跑、钉版本、md5 锁定、三步前置探活 | 环境差异、版本漂移、时序问题 | 脚本自身的问题 |
  | **执行层** | 换人**跑同一个脚本** | 结果可复现性 | **断言本身把期望写错** |
  | **断言层** | 换人**用自己的探针独立重实现**（自带载体合法前置 + 正对照） | **断言级错误**（字段名、空态、载体、范围） | 需要更多时间 |

  · 实例：t43 那次事故的本质是**断言层**问题（越权方根本没有教师身份）—— 前两层都发现不了；
  · **断言层的前提：期望值必须独立于被复核者的断言文本**（2026-09-12 study-eng）。链路应为：
    **需求原文**（例：「任一教师不得改动不属于其任教范围的考试分数」）→ **复核方自己**推出"越权 POST 应被拒且 DB 不变" → 用**他自己的探针**实现并验证。
    若他只是**照被复核者的断言复述期望**（哪怕换了实现），得到的是"我那份理解的一个独立实现"，**不是独立理解** —— 被复核者理解错了，他也会错，而且看起来更权威（"两个人独立确认"）。
    → 实践：请求独立复核时**给判据（前置合法 + 正对照 + DB 读回原值），不要给断言原文**。
  · **结论必须标范围**：哪几条升到了断言层、哪几条仍停在执行层，要逐条写清（例：**6 条中 2 条已升至断言层，其余 4 条仍为执行层**），**不得用粗粒度词把结论放大到证据之外**。
  · 预案必须写清：**断言层结果不一致时，以独立实现方为准**，把差异当 findings 重查，而不是两边各执一词。
  · **「跑两遍」只能证明"稳定"，证明不了"忠实"**（2026-09-12 brand-eng）：要证"输出里的指纹 = 所运行文件的内容指纹"，需**可证伪**三条：① 自己算 `md5` 与输出比对；② **变异测试**（复制到 `/tmp` 改一字节 → 指纹**必须变**，否则说明是写死常量、改造是假的）；③ 同一文件两次运行指纹一致（排除时间戳类噪声）。
- **台账/报告要逐条标注「证据等级」，而不只标注证据**（2026-09-12 i18n-eng 自查）：
  · 例：`check_odoo_trace` 的退出码契约中，`0=OK` 与 `1=FAIL` 是**执行验证**（跑得到），而 `3=INCOMPLETE` 分支**当前无法被观测**（没有未验证面时默认与 `--lenient` 都返回 0）→ **只有代码级验证**；
  · 做法：把「**执行验证 / 仅代码验证**」逐条写进台账，而不是笼统说"已核实" —— 读者需要知道**哪些是被真跑过的**；
  · 这是「验不了 ≠ 干净」这条规矩**指向自己的文档**：**对自己发布的东西也要标等级**。
- **证据三级（2026-09-12 study-eng 细化，接 CLAUDE.md 铁律 0「无法核实的必须标『未验证』」）**：

  | 级别 | 内容 | 写法 |
  |---|---|---|
  | **行为实测** | 事实（此环境、此刻） | 直接陈述，附命令与数字 |
  | **源码/文档语义** | 机制与成立条件（该版本为什么必然如此） | 附 `文件:行号` |
  | **外推**（跨版本/跨场景） | **推断** | **必须标注为推断**，不得当结论用 |

  · 实例：`res_partner.py:229-231` 保证的是**该版本下该字段的语义**（`user_id` 是「销售员」）；由此**可以合理推断**跨版本不会自动回写，但"任何版本都不会"**已是一句外推**，比注释字面更强；
  · 教训：本轮多次"结论比证据走得更远" —— 最典型的是把 6 条断言说成"核心证据"，其实**载体都没验**。
- **行为实测 + 源码解释「配对」才是完整证据**（2026-09-12 flow-eng 补充适用边界）：
  · 行为实测：本环境**碰巧如此**（例：`res.users.create` 没回写 `partner.user_id`）；
  · 源码解释：给出**可推断范围**（例：Odoo 自己在 `res_partner.py:229-231` 注明该字段是「销售员」→ **任何版本都不会自动回写**）；
  · 两者配对才能支撑"这条结论不依赖当前环境"，否则升级/换库后结论可能失效。
- **先证明「补丁/屏蔽本身生效」，再读它造成的结果**（2026-09-12 study-eng，同一风险的镜像形态）：
  · 链路：装补丁（吞掉 `user_id` 写入）→ 调构造器 → 断言抛异常。**风险**：若补丁**没真正生效**（拦截没装上 / `sudo()` 路径绕过 / 包装只作用于某实例），构造器会**正常成功** → 你看到"没抛异常" → **可能得出"守卫没拦住"，而其实是补丁没装上**；
  · 与「验到尺子而不是守卫」是**镜像**：那次是**够不到**守卫，这次是**误判**守卫失灵 —— 两者都是「**负例因为错误的原因给出结果**」；
  · **做法（几秒钟）**：装完补丁后，**先对一个无关对象试写一次该字段，断言它没写进去** —— 写进去了 → 补丁无效 → **停，改补丁**（否则读数作废）；没写进去 → 补丁确实生效 → 此时"抛异常"才是**关于守卫**的证据；
  · 一句话：**这是「先证明量具生效，再用量具读数」的递归应用。**
- **负例失败，也可能是负例自己错了**（2026-09-12 study-eng，t66 前置）：
  · 链路：制造"半合法载体" → 期望守卫拒绝。**陷阱**：若屏蔽手法没真正生效（写到了别处 / 被 compute·inverse 覆盖回去），载体其实**是合法的** → 守卫**当然不报错** → 你会得到"守卫没拦住"的结论 —— **而那是你的测试坏了，不是守卫坏了**；
  · **前置四步**：① 用你的手法造出"漏写"载体；② **先断言该载体确实半合法**（用与 `current_faculty()` 同一判据、或 join 查 `res_partner.user_id`，断言**解析不出教师**）；③ **然后**才调用被测路径，断言守卫**以预期方式**拒绝；④ 若第 ② 步就失败 → **是你的屏蔽没生效，属于本次测试的问题，不构成关于被测对象的 finding**，改手法重试而不是下结论。
  · 这是「负例还要证拦的理由是对的」换个位置再出现：**失败也需要被解释，否则失败本身可能是假红。**
- **负例必须与正例「同批」跑，否则两者不可区分**（2026-09-12 study-eng，t65 设计缺口）：
  · 反例设计：注入任意串 → `-u` → 断言「仍是脏的」→ 声称证明了「机制修不了任意损坏」；
  · **缺陷**：若 `-u` 因故没装载那个 function（模块不在列表 / 注册表出错 / function 被改坏），字段**同样脏** → 断言照样通过 → 得到的不是「能力边界」，而是**「不确定机制跑没跑」**；
  · 修法：**同批做一次正例**（注入已知片段 → `-u` → 断言自愈）；正例过 ⇒ 机制确实跑了 ⇒ 负例的「修不回来」才真是能力边界。**对照关系必须自己成立。**
- **完成载荷里固定一行：「本轮我自己的判据/证据错在哪」（没有就写「无」）**（2026-09-12 study-eng 提，队长采纳为指令）：
  · **为什么**：本轮产出的全部方法论（三层独立 / 恒定先查量具 / 负例自己也可能错 / 语义 vs 表示 / 公告三件套）**没有一条是从设计推出来的，全部来自具体失误** —— 供给源是「**当事人自己把错说出来**」，不是"有人设计得更好"；
  · **风险**：接近收尾时失败压力下降，「自曝」的动机也随之下降，而下次这套东西要继续长，靠的正是压力最大的时候有人肯说；

  · 这与「载体合法性从每个作者的自觉变成构造器的保证」**是同一招，只是用在流程本身**。

  · **必须被汇总**（否则是只写不读）：交付报告里专设一节收集本轮全部自曝（谁 / 哪条判据 / 是否已修），让"个人记录"变成"**团队的失败清单**" —— 与「覆盖率必须是可审计声明」同构：**写了但没人读 ≈ 没写**。
- **不要在明知完不成的情况下开工 —— 也不要在开工之后再报做不了**（2026-09-12 study-eng 的排期纪律）：
  · 它是「**不拿近似当通过**」「**不把没做完的写成做完**」的**对称条款**：前者管"做完之后怎么说"，后者管"**做之前要不要开始**"；
  · 理由很实在：**认领后跑到一半断掉，交付的是一个"已认领但未完成"的任务 + 半成品文件**，比没开始更难收拾（还要判断状态、清残留），且会占用一个并发位；
  · **正确顺序**：**先评估余量 → 报"我不适合起这项"并给出替代方案（转派 / 最小切片 / 硬做的预期）→ 由队长定**；
  · **同一任务连续两次因"做不完"被交回 ⇒ 要处置的是「任务体量」，不是「承接人」**（2026-09-13 study-eng，t108 attempt 3）：
    情形：两文档共 **1,383 行 / ~149 KB** 的逐行通读，前两次（不同人）都因余量不足交回；第三次承接人**先量成本、再报"不适合起"**，并指出**体量问题可复现**；

    通判：**"再试一次同样的规模"不是处置** —— 连续失败要怀疑**任务形状**（太大／太糊／前置不足），而不是承接人的能力。
  · **不要**：先 claim 再报做不了（那时状态已经脏了）；
  · **最小切片是可接受的形态**：若只做"清单 + 草稿表（含每条的自证读数）"就把接力棒交出去，产物是**可交接的中间物**，不是半成品。
- **「中间阶段成功」不等于「证据升级」**（2026-09-12 study-eng）：夹具建成了、前置证过了、清场做完了 —— **但断言没跑出结论，那证据就仍停在原层**。

  · 关键判据只有一条：**「构造器在写被屏蔽的情形下抛异常」，而不是「某个半合法载体查不到教师」。**
- **修"会造成残留的夹具"之前，必须先清掉它历史上的残留**（2026-09-13 i18n-eng，t100 ①）：
  · 情形：某脚本"全部静音"只恢复部分键 → 库里积下 `reimburse_result` / `subject_reg_result` 的 `muted=True` 残留；
  · **陷阱**：修好的脚本会**忠实快照并还原当前状态** ⇒ 若不清残留，它会把**既有污染当成"正确值"原样保下来**，"修好"反而**把污染固化**；
  · 规矩：**先清历史残留 → 再上快照/还原**，并在注释里写明"清理必须在前"的理由。
- **码值选错 = 给失败发一张免死牌**（2026-09-13 i18n-eng，t100 ③，机制已由代码证实）：
  · 情形：某脚本真 FAIL 时 `return 2` —— 非零，看似满足"有 FAIL ⇒ 非零"；但 **2 在本仓约定里特指 ENV** ⇒ 被读数纪律「环境型失败标 ENV 作废」**当场漂白**；
  · **机制**（`assertion_audit.py`）：`ENV_RCS = (2, 3)`，`is_env_run()` 为真即「**本轮不给任何断言记红**」**且不吃 `runs`** ⇒ 该脚本的断言**永远不积累红历史**、一直被留在 REVIEW 名单里，而那份名单问的是「你能描述一个让它变红的场景吗？」—— 答案是「**能，但工具拒绝记录**」；
  · 正确：真失败一律 `1`；**2 只能表示"环境未就绪"、3 只能表示"未覆盖/边界漂移"**；推论：**批量跑对 rc 的分类必须与各脚本真实语义一致**，否则会成批把"真失败"扫进 `env_runs`（那个桶被单列成"比 REVIEW 更该先看"，恰恰因为意味着"连它行不行都不知道"）。
- **每条断言都要能回答：「你能描述一个让它变红的场景吗？」**（2026-09-12 study-eng，下放到断言一级）：
  · **离线证明技法（2026-09-13 i18n-eng，可直接抄）**：把断言的**判定逻辑抽成函数**，用**纯 Python 喂"应该红"的情形** —— 不需要环境、不需要跑站点，**停机期间也能做**；
    实例（4 例，3 例会红）：快照为空 → 前置断言 **FAIL**；正常 → 全 PASS；**还原未生效 → 无残留断言 FAIL**；**还原不完整（只回部分键）→ FAIL 并点名是哪两个键**；
    其中"还原不完整"**正是促使该任务存在的原始 bug** ⇒ 这不再是"加了一条看起来对的断言"，而是"**加了一条经反例检验的断言**"；
    另外，第 1 例（快照为空 → `snap0={}` → 空集恒真）**是刻意堵掉的假绿退路** —— 与"空模式匹配一切"同族；**加一条"快照已取"的前置断言即可堵住**。
  · **能描述**（例：「清场没删干净就会红」）→ 有效断言，只是这轮恰好没触发；
  · **描述不出** → **它从没打算被判假**，等于占位符；
  · 这是「门禁要能自证会红」**下放到每一条断言** —— 同一句话，量程小一号；
  · **为什么需要**：判据活在 prose 里就**不会在赶时间时触发**；靠「再多念几遍」作用有限 —— 凡是靠「记得」的判据，都会在压力下让位于「先把它跑通」。要它当场触发，只能挪进**工具**；
  · 配套自动检测：**记录每条断言的 pass/fail 历史，「连续 N 次从未红过」标记为 REVIEW** —— 恒**假**一眼可见，真正危险的是恒**真**：**一条从来没红过的断言是隐形的**，它可能一直在证明一个不需要证明的东西。
- **判据输出"恒定"（恒 0 / 恒空 / 恒真）时，先怀疑判据本身，而不是先怀疑产品**（2026-09-12 study-eng 的识别启发式）：**真实的违规分布几乎不会是常数** —— 恒定往往意味着量具坏了（列不存在、字段名错、过滤条件恒假/恒真）。
  · 实例（t65/探针）：SQL 直查 `op_faculty.user_id`，而它是 `_inherits res.partner` 的**委托字段**、SQL 侧无此列 → **命中恒为 0** → 假红；改为 join `res_partner.user_id` 后通过；
  · 与「抽不到即不通过」配套：**恒定的绿与恒定的红，都先查量具。**
- **断言要盯「语义不变量」，不要盯「表示形式」**（2026-09-12 study-eng，t65 那条例外的定位）：
- **当"产出物本身就是给人看的那行字"时，断言必须锚在输出文本上，而不是内部变量**（2026-09-12 study-eng 的方法更正）：
  · 场景：门禁的**核心价值就是"点名"**（报出哪条引用有问题）；它一开始想断言"内部用了 `cands[1]`"这类**实现细节**，后来改为用 `redirect_stdout` **捕获打印文本再断言**；
  · 理由：**用户看不见 `cands` 变量，只看得见那行 FAIL** —— 验实现细节会**与目标错位**；
  · 通判：**先问"这件东西的产出物是什么"** —— 产出物是给人看的文本，就断言文本。
  · 实例：把"任意串不自愈"写成「`-u` 后**字节**是否等于注入值」→ **恒假**（写回时框架把值规范化成 `<p>…</p>`）→ 正确判据是「**品牌词是否还在**」；
  · 与前几个变体的区别：那些多是「**取错了值**」（子串启发式 / `bool(recordset)` / 数字子串 / `None==None` / SQL 查委托字段），这一条是「**取对了值、比错了东西**」；
  · 通则：盯**语义不变量**（品牌词在不在 / 数据变没变），不要盯**表示形式**（字节、DOM 结构、序列化形态）—— **框架会规范化它们**；
  · 识别信号与「恒定输出先查量具」合流：**"永远不成立"的判据就是恒假**，先查判据。
- **公告的价值在「事后可核对」，不只在「事先打招呼」**（2026-09-12 i18n-eng 实证）：
  · 实例：活数据窗口 15:05:30–15:07:59，某人的两次相关读数分别在 **15:05:00（窗口开启前 30 秒）** 与 **15:10:20（还原后）** → `10/47` 结论成立；**若第一次晚 90 秒落下，就会读到 11/47 并误判自己回归了**；
  · **事先公告更好，但迟到的公告只要带齐特征，仍能把"猜"变成"核"**；
  · 特征三件套：**窗口边界 + 异常签名（如"数据面会多 1 条命中"）+ 复原证明（md5 一致 / 门禁回到 0）**；
  · **出口侧要求**：工具输出必须**自带运行时间戳**（否则保存下来的读数无法自证何时跑的 —— 文件 mtime 一复制就没了）。
- **公告必须带「可识别的信号」**（2026-09-12 study-eng）：**时间窗口 + 受影响的条目名 + 期望的计数偏移**。
  · 只给时间范围，后来人无法把"我看到的这一条命中"对应到"那次测试"；带上条目名与计数偏移，**该窗口内的读数才是自证的**。
- **没演练过的还原 = 不确定的还原**（2026-09-12 study-eng）：与"备份必须演练过才能算备份"同一条；
  · 动活数据的五步：**dump 库外 → 先公告窗口（三件套）→ finally 还原 → 读回断言 → 再跑门禁确认回到 0 命中**，其中**还原脚本本身要先演练一次**。
- **判据过严也会制造假红**（2026-09-12 brand-eng，t65 第 2 条用例）：它最初把"任意串不自愈"写成「`-u` 后**字节**是否等于注入值」→ 得 false；查因发现**写回时值被 Odoo 包装成 `<p>…</p>`** → 字节相等是过严判据；正确判据是「`-u` 之后**品牌词是否还在**」。
  · 通则：**判据要贴着"要证明的那件事"写**，而不是贴着某个**实现细节**；**过松（假绿）与过严（假红）都由"判据与被证对象的错配"引起。**
- **判据的字段名写错，同样会制造假红/假绿**（2026-09-12 verifier，公告线 JSON 面）：它第一版按 `title` 取值得出"两边都 0"的**假象**，实际载荷字段是 `id/badge/text/cta/url`。
  · 与「`bool(空 recordset)`」同族：**判据本身写错**时，红与绿都不可信；
  · 做法：**先确认被观测对象的真实结构**（打印一次原始载荷/响应），再写断言。
- **「列表页不显示」≠「拿不到」**（2026-09-12 t23 复核固化）：同一条受控内容必须在**三条路**上各自判一次：
  ① 搜索 / 列表页；② **详情直链**（断言 303/404 且正文不含标题串）；③ **API / 导出**（CSV / PDF / 接口）。
  **只测第①条就宣布「隔离成立」，等于用更弱但更容易通过的判据替代真正要证明的东西。**
  并且判据要**成对**：反例不可见 + 正例仍可见 + 目标人群仍可见 —— 否则「什么都搜不到」也能伪造成通过。
- **「不漏也不多报」是同一纪律的两端**：越权 id 静默忽略、不计 skip（计 skip 等于向调用方确认该 id 存在）；查询串回显不算命中（页面回显查询词≠内容泄露）。**判据要能被反例证伪。**
- **不可复现部分的标注方式本身就是可审计性的一部分**：补一张「前后都绿」的截图反而会掩盖时间线；正确做法是写明「该段以某人某次的一次性报告为准，我无法独立复核」。
- **一处弱判据往往是一族弱判据的征兆**（2026-09-12 study-eng，t43 自查）：它发现"还原断言在 `restored=None` 时退化成 `None == None` 却判 PASS"后，没有只修那一处，而是意识到 **只要基准值 `before` 本身是 None，所有 `after == before` 都会一起假绿** —— 于是加了一道总守卫「夹具基准值必须可读（非 None）」。
  · 做法：发现一处弱判据时，**先问"它的前提在什么情况下会一起失效"**，再加一道覆盖全体的前置断言，而不是逐个补丁。
- **对照组是判据强度的一半**（2026-09-12 study-eng，接缝测试设计）：
  · **没有对照组，「两边都报」可以靠「什么都报」伪造**；同样地，**没有正向对照，「什么都没报」可以靠「功能被锁死」伪造**。
  · 因此每个否定断言都要配一个**必须成立的正向对照**（例：越权 id 不生效的同时，属主操作必须成功；定向公告对学生不可见的同时，全体公告必须仍可见；接缝测试里"至少一方报"必须配"纯中文两边都不报"）。
  · 这是本轮反复栽的那个坑的**反面表述**：凡是**用更弱但更容易通过的判据替代真正要证明的东西**，都会在"看起来全绿"里结束。
- **接入新检查时不能"非零即拒"，必须按退出码契约分级**（2026-09-12 本日第二次同型事故）：把 `check_view_xpath` 接进 `safe_upgrade` 后，检查器一旦返回 `INCOMPLETE`（exit 3，边界型未覆盖），升级就被健康检查自己挡死 —— **全队升级链再次中断**。
  · 正确做法：`0=OK` 通过 ｜ `1=FAIL` **唯一拒绝升级** ｜ `2=ENV` 与 `3=INCOMPLETE` **仅提示、不拒绝** ｜ 其它非零码按不拒绝处理并提示留意；
  · 通则：**一个检查的退出码语义是它的契约**，调用方必须按其分级处置；"只要有非零就拒绝"等于把检查器精心区分的三类重新拍平。
- **门禁被"同时管理该资源的脚本"调用时，必须在获取资源之前运行**（2026-09-12 自锁假红 P0）：
  · 事故：`safe_upgrade.sh` 先 `mkdir $LOCK` 取锁、**随后**才调 `check_view_xpath.py`；检查器解析同一个锁路径 → 把**调用者自己的锁**当成"他人持锁" → SKIP-ENV → 拒绝升级 → **全队升级链断掉**。
  · 这是**假红的镜像**（不是"看起来绿其实红"，而是"看起来环境没就绪，其实是自己挡自己"），也是本轮**第三起顺序类事故**。
  · 正确做法：① 检查移到**取资源之前**（只读类检查本就不需要锁）；② 调用侧把**「因环境被跳过」与「检查失败」分开**（前者继续等待，后者才拒绝）；③ 检查器 docstring 写明调用契约，输出文案区分两类。
- **扫描口径 = 只扫「能到达用户」的路径**（2026-09-12 t41/t44 设计裁定）：
  · 反面：对**已经断掉渲染路径**的数据做扫描，会产生**无法到达用户的假阳性**——与漏报同样有害（假阳性会训练大家忽略门禁）；
  · 但也不许沉默：不可达的数据要么**从根上清掉**（优先，例：清掉 digest.tip 的 Odoo 营销文案，靠 function 每次 -u 重放），要么**显式声明为未渲染来源**并计入「未覆盖」行；
  · 顺序偏好：**让盲区不存在 > 声明盲区 > 沉默地漏掉**。
- **XML 注释里禁止出现连续两个 `-`，包括装饰性分隔线**（2026-09-12 两人各踩一次）：brand-eng 在注释里写 `--mail`、i18n-eng 用 `----` 做分隔线，都被自检拦下。**分隔线请用「····」或「====」**。
  · 与下一条并列：**改视图/数据文件前先过 XML 自检**（`python3 -c "import xml.etree.ElementTree as ET; ET.parse(...)"` 或直接跑 `scripts/check_view_xpath.py`）。

- **claim 与证据要同级**（2026-09-12 t7/t13 教训）：写"唯一入口、全部留痕"这种 claim 时，**必须配同级的证据**——读代码只能证明"代码看起来会写"，只有**写一次再看留痕表**才能证明它真的写了。
  · 判据模板：**做一次 → 断言应有的那一行存在且字段正确 → 还原 → leftover=0**（正向断言优先，防"恰好没数据所以恰好通过"）；
  · 这类验证应固化为**可复跑冒烟**，而不是一次性的会话结论。
- **门禁的「归因策略」有三种，可信度不同 —— 看结论前先看它是哪一种**（2026-09-12 flow-eng + brand-eng）：

  | 策略 | 做法 | 能否据以动手 | 例 |
  |---|---|---|---|
  | **结构推导** | AST + 导入序/模板继承推导 | **可以**，直接给 `文件:行号` | `check_view_xpath` 规则 7 |
  | **子串匹配** | 命中的串回查文件文本 | **只能当线索**，须回渲染实测确认 | `check_english` 的「来源」列 |
  | **不做归因** | 只报"渲染证据 + 样本"，不声称出处 | 由人定位（避免误导） | `check_odoo_trace` |

  · 为什么要有第三种：「来源」列已被证明**骗过三个人**（短词命中定义行、docstring、CSS 类名）→ 与其给一个可能错的出处，不如**只给证据**；
  · **「不做归因」不等于"什么都不给"**，而是给**一组足以机械定位的渲染证据**：`规则类型（如 attr-odoo-value）` + `页面/路由` + `片段`，再配**渲染字节数**与**运行时指纹**。人拿到这四样，定位就是"照页面去那一页的模板/数据里搜片段"，**不需要来源列**；
  · **公式（2026-09-12 brand-eng）**：**归因的价值 = 缩短定位路径；归因的风险 = 让人跳过验证。**
    - 子串匹配：缩短得少、风险大（已骗过三个人）→ **该省**；
    - 结构推导：两样都赚（规则 7 给 `文件:行号`）→ **该留**；
    - 不做归因：把"缩短"这一步交回给渲染证据 → **只有当证据包足够机械时才能这么选**（这就是为什么每条命中都配页面 + 片段，而不是只报一个计数）。
  · 通用判据：**读者必须先问"这条归因是怎么算出来的"，再决定能否据它改代码**。
- **归因可信度取决于它是「结构推导」还是「子串匹配」**（2026-09-12 flow-eng）：
  · **结构推导**（如 AST + 导入序号推出的 `文件:行号`）→ 可以据以直接定位并修改；
  · **子串匹配**（如 `check_english` 的「来源」列）→ **只能当线索**，必须回到渲染实测/前后对照确认；
  · 判读规范：看一条归因**先问它是怎么算出来的**，再决定能否据它动手。
- **门禁的「来源」列只是线索，判据永远是渲染实测 / 前后对照**（2026-09-12，这条已骗过三个人）：来源归属是**子串启发式**（视图优先、词边界、短词易命中定义行），据此去"改那一行"常常改错地方（例：有人按来源列去改一个可见文案本就是中文的按钮）。
  · 正确顺序：**先看渲染结果 → 再定位来源 → 改完用前后对照证明**。
- **判据必须是「渲染结果」，不是「原始值 / arch 文本」**（2026-09-12 t44 实例）：core 的 `_compute_preferences` **原始返回值里那个 `/odoo/digest.digest/1` 链接始终存在**（改不了 core），只有在**模板层**整块替换后才在渲染结果里消失。

- **管道会吃掉退出码 —— 这条对人是复发的**（2026-09-12 两位成员各栽一次）：`python3 x.py | tail -2; echo $?` 打印的是 **tail 的**退出码，不是 x.py 的。

- **「写入时映射」与「渲染时映射」不可互推**（2026-09-12 t28 判据）：

  · **渲染时映射**（库里存原码、显示时映射）→ 改代码**自动覆盖历史**，不需要动数据。

  → 附带要求：兜底逻辑**不得回落成原始码**（空值/未知值 → 中性中文，而不是把 `activate` 这类英文码直接给用户看）。
- **验收判的是"渲染结果"，不是"代码改没改"**（2026-09-12 t9/t28 教训）：典型陷阱 —— 审计动作的中文映射若只在**写入路径**补键，新记录正常，但**历史行照旧显示英文** → 验收必须覆盖历史数据（清洗旧值，或在**展示层**做兜底映射）。同理：门禁报绿要以**页面实际输出**为准，不能以"我改了那行代码"为准。
- **升级锁只对 safe_upgrade 生效，直连 `odoo -u` 会绕过它**（2026-09-12 brand-eng 的 EXIT=255 实证）：

- **读"工具自己写的日志"而不是终端回滚**（2026-09-12 第三次过期快照）：报"升级被拒"时，权威读数是工具**自己落盘的那份日志**（如 `safe_upgrade` 写的 `/tmp/edu19_viewxpath.log`，含 mtime）；

- **设计说明与内部标识不得出现在渲染节点里**（2026-09-12 t22 门禁扩面后首次扫描命中）：`views/study.xml:156` 把设计笔记抄进了 UI——「链接存于 Odoo 原生会议链接位（`calendar.event.videocall_location`），不自建 URL 体系」。**设计说明写进 XML 注释（`<!-- -->`），不要写进会被渲染的文本节点**；用户可见文案里不得出现字段名/模型名/`Odoo`/`/web#`。同类陷阱还有：`template` 的 `name` 属性、docstring、CSS 类名——它们都不渲染，但**扫描器/人都会把它们当文案读**，所以门禁的"来源归属"必须能区分渲染路径与元数据。

- **AgentTeams 铁律：任务契约里的 `verify` 命令，必须先在本机跑通一次再写进任务**（2026-09-12 教训）。运行中的团队计划**不可编辑**，所以一条不可执行的 verify 命令会**永久锁死该任务及其全部下游**——v3 的 t5 因此被迫重开 4 次。同理：`inScope` 要按**实际会改到的文件**列全（含 `__init__.py`、新建的 `models/` 等），漏列会让实现无法标记完成；契约外确有必要的改动，走「队长书面授权 + output 显式列出」并保持可追溯，**不要把已知改动藏进未声明的路径**。

- **对比度门槛按字号分档 —— 而 axe 对 14px 按钮文字同样按 4.5**（2026-09-14 t111 实测，错在队长）：WCAG 的 3.0 档只适用于**大字**（≥18.66px 粗体 / ≥24px）与纯装饰性大色块；**按钮 / 链接 / 正文一律 4.5**，哪怕它当的是"底"——白字压 `#0E7BF2` 实测 26 条 `expectedContrastRatio=4.5`。
  · 规矩：**交办口径里凡出现"精确数值门槛"，写进任务前必须先用目标量具跑一次反证**（找它的判据常量或实测样本），否则一句凭印象写的门槛会让整轮执行走偏。
- **「自家样式打架」造成的对比度缺陷，比配色本身更隐蔽**（2026-09-14 t111）：页脚 **69 条**奶油色字压白底（**1.16:1**）的根因不是配色，而是**我们自己**的换肤规则 `custom_home.css` `#wrapwrap.o_portal footer,.o_footer{background-color:…!important}` —— 用**特异性 + `!important`** 把 `brand.css` 的深底盖回浅底，**字色没跟着改**。

- **多轮任务要切片，并把「failed」的语义写进台账**（2026-09-14 t111 → t112 → t113）：当契约验收（如"违规归零"）天然是"**测量 → 改 → 再测**"的多轮过程时，把它切成 N 个"**一轮一交付**"的任务，并明确：**中间轮判 failed ＝ 切片完成、残余转下一轮，不是质量事故、不是返工**。否则台账上会挂一串 failed，读起来像连续失败。
  · 配套两条：① 每轮失败的 `findings` 就是下一轮的**施工单**（带 `文件:行号` + 实测条数），**不要让下一位重爬代码**；② **运行中的团队不可改契约字段** ⇒ 切片必须在**交办时**就写进 acceptance，事后补口径只能靠 `reason` 与消息，且要在报告里如实登记。

- **「半覆盖」是独立的缺陷族：覆盖了底、没覆盖字**（2026-09-14 t111 的 f5 更正）：凡"我们盖了背景色"的地方，都要同时回答「**字色归谁管**」—— 主题给的 `--badge-color`、我们自己早年定的 `--text-*`、或全局表头规则，都可能把深字留在深底上（实测三例：`/student/timetable` 表头深底压深字、`.text-bg-primary` 徽标 2.19:1、页脚主题深底被我们刷白）。
  · 修法二选一：**要么收回越权的背景覆盖**（首选，一行 `:not(...)` 之类），**要么把配套字色一起覆盖**；**只改背景就是制造对比度缺陷**。
  · 排查口诀：**先问"这块底是谁定的"，再问"这块字是谁定的"** —— 两个答案不一致时，缺陷就产生了。
  · **两个方向都要成对，实测各有一例**（2026-09-14 a11y-eng）：**① 只换底不换字** → `.text-bg-primary` 徽标：主题给的是 `--badge-bg:#e6f0fc + --badge-color:#014892`，我们**只覆盖了 background**（前景仍走主题深蓝）⇒ 深蓝压蓝 **2.19:1**；**② 只收回底不收回字** → 页脚：只排除换肤规则、不排除 `footer a{color:var(--brand-500)!important}` ⇒ 深底配深蓝链接。
  · **镜像情形：收回覆盖时也要成对收**（同上）：页脚换肤若**只**排除背景规则、**不**排除页脚**链接**规则，就会变成"深底配深蓝链接"—— **比不改更糟**。凡"覆盖 / 收回"的动作，都要问一遍「**底与字是否成对**」，两侧同改（实测落地写法：`#wrapwrap.o_portal footer:not(.yylc-footer)` 同时排除换肤与页脚链接两条规则）。

- **运行中的团队：依赖是"写死"的 —— 别把依赖指向可能 failed 的切片任务**（2026-09-14 t111→t112 死锁实录）：
  · 现象：`t112.dependencies=["t111"]`，而 `t111` 以 **failed 终态**结束（实现者按契约如实判 failed）⇒ 调度器报 `blocked by unfinished dependencies: t111`，同时 `t111` 报 `terminal task t111 is immutable` ⇒ **两边都动不了，整条 A 组被一条元数据卡死**。
  · **根因不是谁做错，而是契约设计**：把"天然多轮"的工作切成 N 个任务时用**硬依赖**串起来，等于把"上一轮必须判 completed"设成下一轮的前置条件 —— 而切片轮按契约**本来就该判 failed**。
  · 三条改法：① 切片之间**不写硬依赖**，改用"同一成员 + 顺序约定"；② 依赖只指向**确定会 completed** 的任务（审计、造数、探查）；③ 万一已写死，**唯一解锁路径是让被依赖任务的 owner 自己终结它**（重开 → `cancelled`）—— 队长**改不了别人的契约字段**，运行中的团队也没有任何工具能改 acceptance/inScope/dependencies。

- **HTTP 探活在"系统代理开着"时有两种坏法，第二种是假绿**（2026-09-17 docs-eng，t12）：
  · **①代理连不上** ⇒ \`ProxyError\` ⇒ 站点健康也报「环境不可用」**exit 2（假红）**；
  · **②代理能连** ⇒ 拿回 **502 响应**（\`requests\` 只在网络层抛异常，**502 是"正常响应"**）⇒ 探活**静默"通过"**，等于什么都没探 ✗。
  本机代理 12450 活着时走的正是 ② ⇒ 记牢：**没红 ≠ 没问题**。
  · 规矩：探活必须能**区分三种状态**（站点好 / 站点坏 / 被代理挡）——即断言**状态码候选集**（例如 200/302 才算好），
    而不是"没抛异常就算好"；修法 = \`trust_env=False\`（或显式 \`proxies=None\`），并在注释里写明理由（防止被改回去）。
  · 验证形态（t12 的做法，可复用）：① 用**死端口**构造确定性的代理故障来复现假红；② 修后同条件不假红；
    ③ **反证**：真不可达时必须仍 exit 2（防"放宽成永远通过"）。

- **夹具的"清场"必须覆盖"它改过的既有对象"，不只是"它新建的行"**（2026-09-17 verifier 定案根因，代价是演示数据被清空 + 排查数小时）：
  实况：\`tests/smoke/subject_bulk_scope.py\` 的夹具**克隆 id 最小的行并继承其字段**，而那一行是 \`doc_type=course_change\`（全库分布 course_change ×11 / subject_registration ×1）
  ⇒ 克隆夹具全带 course_change ⇒ **只对 \`doc_type='subject_registration'\` 生效的空单防呆不适用** ⇒ 空 payload 被写回 ⇒ **学生 5 的档案被清成 0 门**。
  脚本删掉了它**自己建的行**（leftover=0），但**它改过的既有对象没人还原** ⇒ 表面"干净"、实际留下持久副作用。
  · 两条规矩：① **夹具不得克隆语义字段**（\`clone()\` 会继承 \`doc_type\` 这类语义 ⇒ 必须显式设定）；② **清场要还原被改的既有对象**
    （写完断言后把目标对象的字段恢复原值，并**验证恢复**），否则"leftover=0"是**只覆盖一半**的假干净。
  · 反查方式：**跨表同刻配对**（批量审批行 ↔ 单条审批行同微秒）+ 源码里"防呆适用条件"的 \`doc_type\` 判据。

- **破坏性实验的协议（把"强推断"钉成"观测"的唯一安全做法）**（2026-09-17 verifier 实践，队长批准）：
  背景：根因结论只剩强推断（相关单据已被脚本清场删除、\`doc_type\` 无法回溯）⇒ 要么挂着"推断"，要么做一次**可逆**实验。
  · **① 前置**：安静窗口（\`pgrep '^python3 tests/smoke/'\`=0 **且** 无升级锁）才算数；
  · **② 跑前**读目标对象**三要素**：字段值 + \`write_date\` + **触发单据**（跨表同刻定位）；
  · **③ 只跑一次**，并记录脚本自身读数与出口码；
  · **④ 跑后**同读三要素 ⇒ 若发生预期变化**且触发单据同微秒**，**推断即转为观测**；
  · **⑤ 立即恢复**（同一批命令内，本例 18 秒），并**复核下游前提**（本例：档案非空 ⇒ 另一个冒烟的防呆前置成立）；
  · **⑥ 登记**：写明"经批准、影响面（哪个库/哪些行）、破坏窗口时长、恢复读数、批准依据"。
  · 边界纪律：即便实验成功，结论仍是**本次观测**，**不外推**成"所有脚本都如此"；实验中看到的旁支写入**不归因**（无唯一定位就写"观察到、未归因"）。

- **断言里的数字不能用裸子串匹配——小值域上近乎恒真**（2026-09-17 verifier 自己抓出的假绿）：
  旧写法 \`'14' in page_text\`：他 16:12 那次跑完实测档案**只有 1 门**，而 #10 仍判 **PASS** ⇒ 那个 \`14\` 是**被页面里其它数字撞上的**（日期/id/别的计数）
  ⇒ **该判据的"数字"那一半根本没在验"档案有 14 门"**，验的是"页面某处出现过 14"。⇒ **旧判据是双向不可靠：既假红也假绿。**
  · 正确写法（经采纳）：**把数字从它所在的上下文里抓出来再比**，例如 \`re.search(r'已有\s*(\d+)\s*门科目', text)\` 的捕获组 == 实际值；
  · 配套：无论哪种写法，都必须**能被变异测试打红**（把期望值改成 \`实际值+999\` ⇒ 必红），否则无法区分"判据对"与"判据恒真"；
  · 同族：**裸子串 / 无正对照 / 无负对照 / 走错通道 / 没区分度** —— 都是"看起来验过了"的变体。

- **不要用 \`eval\` 去"抽取"脚本里的变量片段 —— 多行脚本会把尾部一起执行**（2026-09-17 docs-eng 近失事故，无副作用）：
  他为了对拍锁路径，\`eval\` 了 \`safe_upgrade.sh\` 里的 \`LOCK=\` 行；但**结束模式写错**（变量名猜成 \`UPGRADE_LOCK\`）
  ⇒ awk 没截住 ⇒ **该脚本的尾部被真跑**（跑了三个 gate 与挂载自检，最后在 \`$ACTION\` unbound 处退出）。
  · **为什么没出事**：\`safe_upgrade.sh\` 自带 \`trap … cleanup\`（锁被清掉、实测两处锁路径都不存在）、站点仍 302、容器未重启、无升级进程 —— **运气 + 脚本自身的防御**。
  · 正确做法（他改用后才有可信读数）：**按口径现算路径**（自己写解析），**不要执行外部脚本的片段**；
    必须执行片段时，用**结构化提取**（如 \`bash -c\` 只 source 一个受控文件、或正则取单行）并**先打印将要执行的内容**。
  · 报备形态值得照抄：**明示事故 + 逐项验证无副作用（锁/站点/容器/进程/残留文件）+ 换方法重跑** —— 而不是"重跑一遍当无事发生"。

- **扫描面为空时报 PASS 是假绿**（2026-09-17 perm-eng 自抓两例）：静态检查里 REPO_ROOT 上溯少了一层 ⇒ **扫到 0 个文件却报 PASS**；
  同类第二例：取值正则写窄被 eval() 里的引号截断 ⇒ **孤组 record 漏报**（少报同样是假绿）。
  · 规矩：静态检查必须把「**扫描面计数**」打进输出（X 文件 / Y 节点），且**扫描面为 0 即 FAIL**；
    判据要覆盖两种写法（menuitem 的 groups= 与 record 形式 ir.ui.menu 的 group_ids 字段）；**排除边界要声明并计数**（基座原生设计、声明式策略数据）。
  · 例外纪律：例外清单逐条登记（路径, 菜单 id）→ 理由；**即使为空也每次打印条数**；**已失效的例外要被点名**；不得用「放宽断言」或通配来替代例外。

- **声明式 XML 会把未声明的字段默认成真 —— 升级即复活旧值**（2026-09-17 signup-eng 在 t13 里主动堵的口子，本夜第三次同类）：
  现象：\`edu_nav\` 把两个合并根写成 \`active=False\`（收口值），但**引用方** \`edu_portal\` 的 menuitem 没写 \`active\` ⇒

    并注明「此处与 X 模块的收口值一致，改任一处需同步」；**收口值与声明值必须能互相对上**，否则升级即漂移。
  · 验证形态：**连续两次 \`-u\` 后复测**（本例：两次升级后 542/606 仍 active=f、无重复入口），并给前后计数（605/停用200 → 607/停用200）。

- **文档里不要用行号引用，用描述性引用**（2026-09-17 docs-eng 在 t18 自抓）：他写的更正块引用了「下面第 95 行」，

- **新增 .py 文件（以及任何模型/字段改动）必须重启 web 进程 —— 注册表重载不是重启**（2026-09-24 生产事故后立；代价是生产三个功能暗着 —— 班级管理约 5 天 18 小时、课代表约 2 天 23 小时、专业/学制约 1 天 23 小时）：
